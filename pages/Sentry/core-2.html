Data Modeling

The Interviewer Prompt

"Show me your data model — entities, relationships, and key indexes. Why did you make the denormalization choices you made? How do you handle tag-based multi-dimensional queries? How do you manage write contention on counters at 100K events/second? And how does the fingerprint-to-issue mapping stay consistent across distributed ingestion nodes?"

NO HIRE
L4 / Weak L5 Signal
▼
What They Say
"For the data model I'd have a few tables. A users table with id, name, email, password. A projects table with id, name, organization_id, and created_at. An errors table with id, project_id, message, stack_trace, timestamp, and status. And maybe an organizations table.

For indexes I'd put an index on project_id in the errors table so I can query errors by project quickly. And probably an index on timestamp so I can sort by time.

I'd use PostgreSQL for this. It's reliable and most companies use it."
Fatal Mistakes
  • No events vs issues separation — the most fundamental data modeling mistake for this system. Raw events and grouped issues are completely different entities with different access patterns, different storage requirements, and different retention policies.
  • Stack trace stored as a text column — at 10KB per event × 8.6B events/day, this is a catastrophic design choice in a relational DB column.
  • No fingerprint/grouping model — the core feature of the system has no data representation whatsoever.
  • No mention of write volume — PostgreSQL at 100K writes/second with 10KB payloads is immediately saturated.
  • "PostgreSQL because most companies use it" — cargo cult reasoning, not architecture reasoning.
  • Single-column indexes on project_id and timestamp separately don't serve the dominant query pattern: "all open issues for project X sorted by last_seen."
Interviewer's Notes

"Conflated events and issues into a single table — doesn't understand the core data model of the system. Stack trace as a text column at 100K writes/second would destroy any relational DB. No fingerprint model. 'PostgreSQL because everyone uses it' is not an engineering answer. Significant data modeling gap."

LEAN HIRE
Meets L5 bar — not L6
▼
What They Say
"The key insight for the data model is separating raw events from issues. An issue is a group of similar events — they're fundamentally different entities with different access patterns.

Issues table (PostgreSQL): issue_id, project_id, fingerprint, title, culprit, status (open/resolved/ignored), first_seen, last_seen, times_seen, users_seen, environment, level, assignee_id, created_at. Index on (project_id, status, last_seen) for the main dashboard query.

Events table: event_id, issue_id, project_id, timestamp, platform, level, environment, release. I'd store the raw event payload — stack trace, breadcrumbs, tags — separately in object storage like S3, not in the relational DB. The events table just stores queryable metadata.

Tags table: tag_id, event_id, key, value, project_id. This gets complex — tags are arbitrary key-value pairs and there are a lot of them.

For the fingerprint-to-issue mapping, the fingerprint would be a unique field on the issues table with a unique index on (project_id, fingerprint). When a new event comes in, I look up the fingerprint, get the issue_id, and increment the counter.

I'd use PostgreSQL for the issues and metadata layer, and S3 for raw event payloads."
What's Good
  • Correct events/issues separation — fundamental insight present
  • Raw payload offloaded to object storage — correct from storage math
  • Fingerprint model present with unique constraint
  • Composite index on (project_id, status, last_seen) — correct for primary query pattern
  • DSN stored in projects table — shows understanding of auth model
What's Missing for L6
  • No tag index strategy — a naive normalized tags table with one row per tag per event creates billions of rows and makes multi-tag queries impossible without full table scans
  • No event search strategy — how do you filter by arbitrary tag combinations at scale?
  • No counter update strategy — UPDATE issues SET times_seen = times_seen + 1 at 100K QPS causes severe lock contention
  • No time-series aggregation — the event frequency histogram requires pre-aggregated data, not a COUNT on raw events
  • Fingerprint TOCTOU race condition — two identical events arriving simultaneously at different nodes both try to create a new issue
  • No multi-tenancy data isolation in the schema
Upgrade Needed to Reach L6

Add a tag indexing strategy: "I'd use a columnar store like ClickHouse for tag-based event search — a normalized tag table in PostgreSQL doesn't support multi-dimensional filtering at this scale." Add a counter update strategy: "instead of row-level updates at 100K QPS, I'd batch counter increments in Redis and flush periodically." Handle the fingerprint race: "INSERT ... ON CONFLICT DO UPDATE — atomic in PostgreSQL, prevents duplicate issue creation."

Interviewer's Notes

"Good separation of events and issues, correct storage strategy for raw payloads. But no tag indexing strategy — that's the hardest query problem in this system. No counter update strategy at 100K QPS. Fingerprint race condition not addressed. Lean hire — needs depth on the hard problems."

Critical Indexes — issues table
  • (project_id, status, last_seen DESC) — primary dashboard query: "show me open issues for this project sorted by most recent"
  • (project_id, fingerprint) UNIQUE — fingerprint deduplication lookup; uniqueness constraint prevents duplicate issue creation
  • (project_id, first_seen DESC) — "new issues this week" query
Denormalization Decision — Counter Trade-off

times_seen and users_seen are denormalized counters on the issue. The alternative — COUNT queries against raw events — is impossible at 100K events/second and 90 days of retention. The trade-off: these counters are eventually consistent. I update them asynchronously via batched Redis increments flushed every 30 seconds, not via synchronous row updates on every event ingestion. This converts 100K random writes/second into ~1 bulk update every 30 seconds per issue. Acceptable given our NFRs — the count shown may lag by up to 30 seconds.

Why Not PostgreSQL for Events?

At 100K writes/second with 90-day retention, that's ~8.6 billion rows. PostgreSQL's row-level MVCC and B-tree indexes don't scale to this write rate. ClickHouse — a columnar OLAP database — can sustain 100K+ inserts/second with background merging and no MVCC overhead. MergeTree tables handle time-series aggregation natively. Partition pruning on toYYYYMM(timestamp) means date-range queries skip entire month partitions.

Tag Multi-Dimensional Query Strategy
"Tags are arbitrary key-value pairs — browser=Chrome, release=v2.1, region=us-east. The query pattern is multi-dimensional: 'show me all issues where browser=Chrome AND release=v2.1.' A normalized tags table in PostgreSQL — event_id, key, value — is a dead end. Multi-tag filtering requires self-joins that don't scale to billions of rows.

Instead, I store tags as parallel arrays in ClickHouse: tags_keys and tags_values. The query pattern — WHERE has(tags_keys, 'browser') AND tags_values[indexOf(tags_keys, 'browser')] = 'Chrome' — handles multi-dimensional filtering efficiently at scale. For the most common tags (release, environment, level), I'd promote them to first-class columns for even faster filtering."
Counter Update Strategy — Avoiding Write Contention
"times_seen at 100K events/second means 100K UPDATE issues SET times_seen = times_seen + 1 queries per second — this creates severe lock contention on hot issues. Instead:

I buffer increments in Redis using INCR issue:{issue_id}:count for atomic per-issue increments. A background job flushes these counters to PostgreSQL every 30 seconds via a single bulk UPDATE. This converts 100K random writes/second into 1 batch update every 30 seconds. Trade-off: 30-second eventual consistency on counts. Acceptable for our use case."
Fingerprint Race Condition — Handling TOCTOU
"When a new event arrives with a new fingerprint, we need to create a new issue. Two events with identical fingerprints arriving simultaneously at different ingestion nodes could both try to create a new issue, resulting in duplicate issues.

Solution: INSERT INTO issues (project_id, fingerprint, ...) ON CONFLICT (project_id, fingerprint) DO UPDATE SET last_seen = EXCLUDED.last_seen RETURNING issue_id — the upsert is atomic at the DB level and prevents duplicates. The RETURNING clause gives us the issue_id regardless of whether we inserted or updated — a single atomic round-trip."

STRONG HIRE
L7 Signal — Exceptional
▼
Opening Framing — Polyglot Persistence
"Before I define individual entities, let me call out the core data modeling tension in this system: we have three fundamentally different data access patterns that pull in opposite directions. Raw event ingestion is write-optimized — append-only, extremely high throughput, no reads during write. Issue querying is read-optimized — low cardinality filters, needs fast aggregation, accessed constantly. Tag-based search is OLAP-style — arbitrary multi-dimensional filtering across billions of rows. No single storage engine handles all three optimally, so this is inherently a polyglot persistence problem. I'll design each layer for its dominant access pattern."
LAYER 1

LAYER 2

LAYER 3
Raw Payload Store
S3 / GCS
Full stack traces, breadcrumbs, HTTP context. Fetched on demand. Key structure enables GDPR deletion and per-org lifecycle policies.
ClickHouse DDL — Production-Ready
CREATE TABLE events (
  event_id     UUID,
  issue_id     UUID,
  project_id   UUID,
  org_id       UUID,
  timestamp    DateTime,
  platform     LowCardinality(String),   -- low-cardinality → dictionary encoding
  level        LowCardinality(String),
  environment  LowCardinality(String),
  release      String,
  user_id      String,
  user_email_hash String,                -- SHA-256, never plaintext
  tags_keys    Array(String),
  tags_values  Array(String),
  payload_s3_key String                  -- reference to full payload
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)         -- month partitions, prune on date range
ORDER BY (project_id, timestamp)         -- clustering key for project queries
TTL timestamp + INTERVAL 90 DAY;        -- automatic retention, no cleanup job needed
Why This DDL Is Exceptional

LowCardinality(String) for platform, level, environment — ClickHouse applies dictionary encoding, dramatically reducing storage and improving filter performance for these repeated values. TTL policy in DDL — instead of a scheduled cleanup job with its own failure modes and operational overhead, the 90-day retention is enforced by the engine automatically. MergeTree ORDER BY (project_id, timestamp) — data is sorted on disk by project and time, making the primary dashboard query (latest events for a project) an index scan rather than a full table scan. Column compression compounds on top: 10KB logical events compress to ~1KB on disk due to high similarity within columns.

Partial/Filtered Index — The L7 Optimization
  • (project_id, status, last_seen DESC) — standard composite index, all issues
  • (project_id, first_seen DESC) WHERE status = 0 — partial index on open issues only. Open issues are ~10% of all issues in a mature system. This index is 10x smaller, has 10x lower write amplification, and fits entirely in buffer pool cache. At 100K issue updates/second, the write amplification difference is the difference between PostgreSQL coping and PostgreSQL becoming the bottleneck.
  • (project_id, times_seen DESC) — "highest volume issues" sort
Hot Fingerprint Shard Routing — The L7 Insight
"For standard fingerprint races, the atomic upsert handles it: INSERT INTO issues ... ON CONFLICT (project_id, fingerprint) DO UPDATE SET last_seen = EXCLUDED.last_seen RETURNING issue_id. The unique constraint guarantees at most one issue per fingerprint, globally. The RETURNING clause gives us the issue_id in a single round-trip regardless of insert or update.

But there's a second-order failure mode most candidates miss: extremely hot fingerprints. During a major production incident, a single issue can receive 10,000 events/second — all with the same fingerprint. At that rate, even the upsert operation becomes a write bottleneck: 10K concurrent writers contending on the same row in PostgreSQL.

Mitigation: route events with the same fingerprint to the same ingestion shard via consistent hashing on fingerprint. hash(fingerprint) mod N_shards determines which ingestion node handles this fingerprint, collapsing 10K concurrent writers to a single writer per fingerprint. This is the same principle as sticky routing in load balancers — we sacrifice write distribution for write serialization on the hot path."
GDPR Deletion — Designed Into the Schema
"Error events routinely capture PII — user emails, IP addresses, and local variable values that may contain passwords. I've addressed this at three levels in the data model.

First, user_email_hash in ClickHouse is a SHA-256 hash, never plaintext. Full PII lives only in the S3 payload with a separate encryption key per organization.

Second, the S3 key structure — raw-events/{org_id}/{project_id}/{YYYY}/{MM}/{DD}/{event_id}.json.gz — enables prefix-based bulk deletion per organization for GDPR right-to-erasure. Deleting an organization means an S3 prefix delete: O(1) operation regardless of event count.

Third, for individual user erasure requests (GDPR Article 17), I'd implement a DeleteQueue: enqueue the user_id, a background job (1) deletes their S3 payload objects, (2) issues a ClickHouse mutation to zero their user_id field, and (3) removes the hashed email. SLA: 30 days as required by GDPR Article 17. The soft_delete flag on organizations handles account-level deletion without immediate cascade."

The Non-Obvious Insight — Partial Indexes

The dominant query is "show me open issues for project X." Open issues are roughly 10% of all issues in a mature system — most issues get resolved. A partial index WHERE status = 0 (open) is roughly 10x smaller than a full index, has 10x lower write amplification, and fits entirely in the buffer pool cache. This is a routine PostgreSQL optimization that experienced DBAs know but most application engineers have never used. At 100K issue updates/second, the write amplification difference is the difference between PostgreSQL coping and PostgreSQL becoming the bottleneck.

🎯 Key Lesson from Phase 3b
Access Patterns Drive Storage, Not the Other Way Around.

The L5 → L6 shift is about solving the hard query problems — tag multi-dimensional filtering, counter write contention, fingerprint race conditions — not just modeling the happy path. The L6 → L7 shift is about framing the data model as a polyglot persistence strategy before touching a single entity, then designing compliance and operational requirements (GDPR, TTL, partial indexes) into the schema at definition time rather than bolting them on later.

Practice this: For every entity you define, ask "What is the dominant query against this entity, and does my index serve that query with an index seek rather than a scan?" Then ask "What happens to this entity at 100x write volume?" Those two questions catch 80% of data modeling gaps.
