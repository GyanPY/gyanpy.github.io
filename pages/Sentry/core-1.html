Phase 1 0 – 5 minutes

Problem Clarification

The Problem — Interviewer Prompt

"Design a system like Sentry." — That's all you get. The floor is yours.

NO HIRE
L4 / Weak L5 Signal
▼
What They Say
"Okay, so Sentry is an error monitoring tool. I've used it before. It basically captures exceptions from your application and shows them in a dashboard. So I'm thinking we need to design something that can receive errors, store them, and display them.

How many users are we expecting? Like, are we talking millions of developers using this, or is it more of an internal tool? I want to know the scale so I can figure out what kind of database to use.

Also, is this going to be real-time? Like, do errors show up instantly on the dashboard? I'm assuming yes because that's how Sentry works.

I think I have enough to get started. So basically, we'll have SDKs sending errors to a backend, and the backend stores them in a database, and then we have a frontend that queries the database to show the errors. Should I start drawing the architecture?"
Why This Fails
  • Opens with a scale question before establishing what the system actually needs to do — a classic L4 signal
  • Assumes product definition based on personal Sentry usage — no curiosity about what's unique or hard
  • No concept of scope control — immediately jumps toward drawing architecture
  • Doesn't ask about who the users are or what workflows matter most
  • Treats error monitoring as a solved, understood problem
Fatal Mistakes
  • First question was a scale question, not a scope/success question
  • Declared "I have enough to get started" with essentially zero clarification
Interviewer's Notes

"Jumped to 'how many users' before establishing what we're building. Assumed product scope from prior tool usage. Asked for permission to start designing within 60 seconds. No depth of curiosity. Would not pass phone screen for L5."

LEAN HIRE
Meets L5 bar — not L6
▼
What They Say
"Alright, so before I jump into the design, let me make sure I understand what we're actually building here. Sentry is an error and performance monitoring platform — it captures exceptions, stack traces, breadcrumbs, and now also does performance tracing. So the question is: which parts of that are in scope for this design session?

I'd want to understand: are we designing the full SaaS product — meaning multi-tenant, thousands of organizations onboarding their apps — or is this more of a single-organization internal deployment? That changes the architecture significantly.

Is error capture the core feature, or are we also covering performance monitoring — things like distributed tracing, transaction sampling, and profiling? I'd prefer to focus on error capture first since that's the core value proposition, unless you want me to cover both.

What's the expected event volume? Are we talking millions of error events per day, or closer to billions? And are we targeting real-time alerting — like, sub-minute from error occurring to developer being notified?

I'll also note: I'm assuming the SDK side is a black box for now — we're designing the backend ingestion, storage, and querying system. Does that sound right?"
What's Good
  • Correctly separates error monitoring from performance monitoring
  • Asks about multi-tenant vs single-org — a meaningful architectural scope question
  • Attempts to narrow scope proactively
  • Identifies SDK as out of scope — reasonable boundary-setting
What's Missing for L6
  • Still asks volume before defining success criteria — the sequence matters at L6
  • Never asks: "What does success look like for this system?"
  • Doesn't ask about existing infrastructure constraints — is this greenfield?
  • Doesn't explicitly call out what they are NOT building
  • Misses: "What is the read pattern?" — querying vs dashboards vs alerting are very different workloads
  • No mention of compliance/data residency — error events often contain PII
Upgrade Needed to Reach L6

An explicit success-criteria question first. A stated out-of-scope list ("I'm explicitly not designing the SDK, billing, or SSO today"). A compliance/PII flag ("Error events may contain sensitive data — is data residency or GDPR a concern here?").

Interviewer's Notes

"Solid L5. Shows product knowledge, makes reasonable scoping choices, asks relevant questions. But the sequence was off — jumped to volume before success criteria. Didn't surface the PII/compliance angle which is critical for error monitoring. Missing the senior instinct to define outcomes before inputs."

HIRE
Meets L6 bar
▼
What They Say
"Before I touch scale or architecture, I want to make sure I'm solving the right problem. Let me ask a few scoping questions.

First — what does success look like here? Is this primarily about reducing developer mean-time-to-resolution on production errors? Or is the core value proposition the discoverability — being able to search across billions of events and find the one error that correlates to a user complaint? Those are different optimization targets and they'd lead me to different designs.

Second — who are the primary users, and what's their core workflow? I'm thinking three personas: a developer who gets paged at 3 AM and needs to triage fast, a team lead who's doing weekly error review, and potentially an SRE doing post-mortem analysis. The latency and freshness requirements for each of those are very different.

Third — scope check: is this a SaaS product serving multiple organizations — multi-tenant — or an internal platform for a single org? Multi-tenancy affects data isolation, storage strategy, and rate limiting fundamentally.

Fourth — what's in scope vs out of scope? I'd propose focusing on: error ingestion from SDKs, deduplication and grouping of errors into 'issues,' storage and querying, and real-time alerting. I'd explicitly leave out: the SDK implementation itself, billing, SSO/authentication federation, and profiling/performance tracing. Does that scope sound right to you?

One more — error events frequently contain stack traces, local variable values, and HTTP headers. That means we may be inadvertently capturing PII, API keys, or credentials. Is data residency or GDPR compliance in scope? That would affect how we design storage, retention, and deletion workflows.

Let me also ask: is there an existing tech ecosystem I need to be aware of, or is this greenfield?"

  • ✅ Success criteria question asked before scale
  • ✅ User persona identification (developer, team lead, SRE)
  • ✅ Explicit scope definition and explicit out-of-scope list
  • ✅ PII/compliance flag — security-adjacent awareness
  • ✅ Multi-tenancy as a scope clarifier
  • ✅ Clear transition signal ("Let me also ask...")

"Those are different optimization targets and they'd lead me to different designs."
"I'd explicitly leave out... Does that scope sound right to you?"
Interviewer's Notes

"Strong opener. Asked about success criteria before scale — that's the right instinct. User persona decomposition was practical and led somewhere useful. The PII/compliance flag was unprompted and shows real production experience with this class of system. Proposed a clear scope and asked for confirmation. Ready to move to requirements."

STRONG HIRE
L7 Signal — Exceptional
▼
What They Say
"Let me take 3–4 minutes here because the clarification phase will save us 20 minutes of rework later. I want to think about this at the problem level before the solution level.

The core job of a system like Sentry is to compress the feedback loop between a production failure and a developer understanding it. That sounds simple, but it actually spans three very different sub-problems: high-throughput, loss-tolerant ingestion of raw events; intelligent grouping and deduplication of those events into actionable issues (which is actually a hard distributed systems problem — you need fingerprinting to be consistent across multiple ingestion nodes); and low-latency querying and search across potentially billions of stored events. These three sub-problems have conflicting requirements — ingestion wants write throughput, querying wants read-optimized indexes, and grouping wants strong consistency for deduplication. So before I start drawing boxes, I want to confirm which of these is the primary challenge you want me to focus on.

On scope: I'd propose keeping in scope — event ingestion pipeline, issue grouping and deduplication, alert rule evaluation and notification dispatch, and issue search and querying. Out of scope for today: SDK design, the frontend application, billing infrastructure, SSO federation, source map processing, and performance/profiling tracing.

On users: I'm thinking three personas with very different SLAs. A developer being paged needs to see the error with full context within seconds of it occurring. That's a freshness requirement of under 30 seconds end-to-end. A team lead doing weekly triage cares more about grouping quality. An SRE doing post-mortem analysis needs ad-hoc querying across historical data with arbitrary filters. Those are three different read patterns that probably need different storage strategies.

Critical compliance question: error events routinely contain stack traces with local variable values, request headers including Authorization tokens, and user-supplied data. We are almost certainly capturing PII and potentially secrets. I'd want to know: is GDPR in scope? Are there data residency requirements? And do we need a scrubbing layer before persistence to strip PII and credentials?

One final question: are there existing infrastructure components I should build around — an existing Kafka cluster, a data warehouse, an alerting platform? Or is this fully greenfield? And is there a hard latency SLA I should be targeting — specifically, what's the acceptable P99 latency from SDK captureException() call to event appearing in the UI?"
AOMB Completeness Checklist — Strong Hire
  • ✅ Frames the problem at conceptual level before asking any questions
  • ✅ Decomposes into three distinct sub-problems with conflicting requirements
  • ✅ Identifies core tension (ingestion throughput vs read optimization vs deduplication consistency)
  • ✅ Proposes explicit out-of-scope list with reasoning
  • ✅ User personas with quantified SLA implications ("under 30 seconds end-to-end")
  • ✅ Multi-tenancy flag with specific downstream implications
  • ✅ PII/secrets scrubbing — non-obvious compliance surface
  • ✅ Data residency / GDPR — regulatory constraint that affects architecture
  • ✅ Asks about existing ecosystem constraints
  • ✅ Asks for explicit latency SLA tied to specific user journey
The "Wow" Moments
"These three sub-problems have conflicting requirements — ingestion wants write throughput, querying wants read-optimized indexes, and grouping wants strong consistency for deduplication." — Core architectural tension named in the clarification phase.
"Error events routinely contain stack traces with local variable values, request headers including Authorization tokens" — Shows they've seen this break in production.
Interviewer's Notes

"Exceptional opener. Decomposed the problem into three sub-systems with conflicting requirements before asking a single question — that's the mental model of someone who has built this class of system. The fingerprinting consistency observation is something I've never heard a candidate surface unprompted. The secrets scrubbing angle is real — we've had actual security incidents from this. Strong hire signal in the first 4 minutes."

Progression Summary — Phase 1
Gap What Changes
No Hire → Lean Hire Ask scope questions, not just scale questions. Show product awareness.
Lean Hire → Hire (L6) Sequence matters: success criteria before scale. Proactive out-of-scope list. PII/compliance flag unprompted.
Hire → Strong Hire (L7) Reframe the problem space before asking questions. Decompose into sub-problems with conflicting requirements. Quantify SLAs tied to user journeys. Surface non-obvious production concerns (fingerprinting, secrets scrubbing).
🎯 Key Lesson from Phase 1
Sequence is Everything at L6. Reframing is Everything at L7.

The L5 → L6 shift is about sequence — asking what before how much. The L6 → L7 shift is about reframing — showing you understand the core architectural tensions before the interviewer has to draw them out of you. If you can name the conflicts inherent in the problem in Phase 1, you've already demonstrated L7 signal before touching a single component.

Phase 2 5 – 10 minutes

Requirements Gathering

The Interviewer Prompt

"Alright, let's formalize requirements. Give me your functional requirements, your non-functional requirements, and your top 3 NFRs with justification. Also — what are you explicitly not building? And what's your DAU assumption and why?"

NO HIRE
L4 / Weak L5 Signal
▼
What They Say
"Okay so for functional requirements, we need: users can send errors to the system, the system stores the errors, users can view errors on a dashboard, and we should have alerting so developers get notified when new errors happen. Also search — developers should be able to search for specific errors.

For non-functional requirements, the system needs to be fast, highly available, and scalable. We don't want it to go down because if it goes down, developers won't know about errors in production. It should also be secure.

My top 3 NFRs are: performance, availability, and scalability. Performance is important because developers need to see errors quickly. Availability is important because the system needs to always be up. Scalability is important because we might have a lot of errors coming in.

As for DAU, let's say 10 million users. I'm not sure exactly, but that seems like a reasonable number for a large system."
Fatal Mistakes
  • NFRs are completely vague — "fast," "scalable," "secure" are meaningless without numbers
  • No SLAs defined — no latency targets, no availability percentages, no durability guarantees
  • DAU pulled from thin air with zero reasoning — "10 million seems reasonable" is not engineering
  • Missed deduplication/grouping entirely — the single hardest functional requirement of this system
  • No explicit out-of-scope list
Interviewer's Notes

"NFRs were buzzwords — fast, available, scalable — with zero quantification. DAU was a guess with no derivation. Missed deduplication entirely, which is the hardest functional requirement in this system. No SLAs. No out-of-scope list. This is an L4 answer. Would not advance."

LEAN HIRE
Meets L5 bar — not L6
▼
What They Say
"Let me split this into functional and non-functional.

For functional requirements: SDK clients can capture and send error events with full context — stack trace, breadcrumbs, tags, user info. The backend ingests these events at high volume. Similar errors get grouped into 'issues' to avoid noise. Developers can query and search issues. Alerts fire when new issues are detected or error rates spike. Issues have a lifecycle — open, resolved, ignored. Notification integrations — email, Slack, PagerDuty.

For non-functional requirements: low latency ingestion — under 100ms for the SDK to get an acknowledgment so it doesn't block the application. High availability — 99.9% or higher. Durability — we can't lose error events. Searchability — across potentially billions of stored events with reasonable latency.

My top 3 NFRs: first, ingestion availability — 99.99%. Second, low ingestion latency — under 100ms P99. Third, search latency — under 2 seconds.

For DAU — Sentry has around 4 million developers. 1 million DAU for active developers. For event volume: 10,000 active projects each generating 10 events per second on average = 100,000 events per second or 100K write QPS.

What I'm not building: SDK, billing, SSO, source map processing, frontend UI."
What's Good
  • Correct FR/NFR separation with reasonable completeness
  • Correctly identifies ingestion availability as top NFR
  • Makes a reasonable attempt at event volume derivation
  • Proposes specific numbers — better than no numbers
  • Explicit out-of-scope list
What's Missing for L6
  • No consistency model named — what happens if event is written to one region but not another?
  • No durability SLA — "we can't lose events" isn't an SLA
  • No explicit read/write ratio stated or used to drive decisions
  • Deduplication consistency not elevated to an NFR
  • Rate limiting as an NFR missed — a noisy SDK client can flood the system
  • No data retention policy driving storage tier decisions
Upgrade Needed to Reach L6

Add an explicit consistency model statement. A durability SLA ("11 nines of durability for raw event storage"). A rate limiting NFR ("per-project ingestion rate limits to prevent noisy tenants"). A data retention policy ("raw events for 90 days, aggregated issue data for 1 year — this drives our tiered storage design").

HIRE
Meets L6 bar
▼
What They Say
"Let me structure this carefully — functional requirements first, then NFRs with explicit SLAs, then what I'm explicitly not building.

Functional Requirements — P0: SDK event ingestion with structured payload (exception type, stack trace, breadcrumbs, tags, user context, environment, release version). Issue grouping and deduplication — raw events are fingerprinted and grouped into 'issues.' This is the core value differentiator and the hardest engineering problem. Issue lifecycle management — open, resolved, ignored, regression detection. Real-time alerting — fire alerts when new issues are detected or error rates exceed thresholds. Issue search and querying — filter by environment, release, user, tag, time range across billions of events.

Functional Requirements — P1: Notification integrations (Slack, PagerDuty, email), basic dashboards, user and team management within an organization.

Not building today: SDK implementation, source map processing, performance/APM tracing, billing, SSO federation, frontend UI layer.

Non-Functional Requirements with SLAs:
Ingestion availability: 99.99%. This is the most critical path — I'd architect ingestion independently from the query path so a read spike can't degrade write availability.
Ingestion latency: P99 under 100ms for SDK acknowledgment. Fire-and-forget — we ack and process asynchronously.
Event durability: at-least-once delivery with 99.999% durability on persisted events. We can tolerate duplicates, not lost events.
Search latency: P95 under 3 seconds. This is an analytical workload, not transactional.
Alert freshness: P99 under 60 seconds from event ingestion to alert notification.

Consistency model: Ingestion is write-heavy — I'll accept eventual consistency on the read side. But issue grouping requires strong consistency on fingerprint matching — two identical events must map to the same issue ID even across distributed ingestion nodes.

DAU and volume: 1 million DAU. For write volume: 50,000 active projects at 2 events/second = 100,000 events/second baseline. Peak during an incident: 10x — 1M events/second. That peak handling is a core design constraint. Read/write ratio: 10:1 write-to-read on raw events, 100:1 read-to-write on the issue layer.

Data retention: Raw events for 90 days, aggregated issue data for 1 year — this drives a tiered storage strategy. Hot storage for recent events, cold for historical."

  • ✅ Write/read ratio identified and quantified by layer

STRONG HIRE
L7 Signal — Exceptional
▼
What They Say
"I want to be really deliberate here because the requirements phase is where most designs go wrong. Let me structure this as: functional requirements by priority, NFRs with explicit SLAs, consistency model, volume model, and explicit non-goals.

Volume model: Sentry publicly reports ~28 billion events per month. That's 28B / 2.5M seconds = ~11,000 events/second average. Peak is typically 5–10x, so design for 100,000 events/second peak write throughput. For reads: 1M DAU × 20 queries/session = 20M queries/day, ~230 QPS average, peak ~2,000 QPS. Write/read ratio: 50:1 on raw event volume.

Storage math done inline: At 100K events/second, each event averaging 10KB including stack trace — that's 1GB/second of raw ingestion. Over 90 days retention = 8 petabytes. That immediately tells me I cannot store raw events in a relational database. I need object storage for raw events and a separate indexed store for queryable metadata.

Rate limiting as explicit NFR: A single misbehaving SDK — an infinite error loop in production, for example — can generate millions of events/second from a single project. Without per-project rate limiting, one bad actor degrades the entire platform. Per-project limits with graceful degradation: drop events beyond the limit rather than blocking the SDK. Default: 1,000 events/second per project.

SLA Summary: Ingestion availability: 99.99%. Ingestion P99 latency: 100ms. Durability: 99.999%. Alert freshness: 60 seconds. Query P95: 3 seconds.

Fingerprint assignment consistency: This is the consistency-critical path, not ingestion itself. Two identical events arriving at different nodes must resolve to the same issue ID. This is the key architectural decision I'll revisit in the design phase."

  • ✅ Volume derived from public data ("Sentry reports 28B events/month")
  • ✅ Storage math done inline — 8PB conclusion immediately implies object storage
  • ✅ Rate limiting as explicit NFR with a real failure scenario
  • ✅ Data retention driving tiered storage — business policy to architecture
  • ✅ Read/write asymmetry quantified (50:1)

🎯 Key Lesson from Phase 2
Every Number Must Imply a Design Decision.

The L5 → L6 shift is about replacing vague qualifiers ("fast," "scalable") with specific, business-justified SLAs. The L6 → L7 shift is about using requirements as architectural drivers — every number you state should immediately imply a design decision. When your storage math tells you "8 petabytes in 90 days," that's not just a number — it's the sentence that eliminates relational databases from your design before you've drawn a single box.

Phase 3a 10 – 15 minutes

API Design

The Interviewer Prompt

"Define your core APIs — endpoints, request/response payloads, and key design decisions. How do you handle pagination for large result sets? Where are your idempotency keys? How do you handle API versioning and backward compatibility? And why did you make the denormalization choices you made?"

NO HIRE
L4 / Weak L5 Signal
▼
What They Say
"Okay so for APIs we need a few endpoints. We'll have a POST endpoint to send errors, something like POST /errors. It takes the error data in the body — the stack trace, the message, things like that. And then we have GET /errors to get a list of errors, and GET /errors/{id} to get a specific error.

For the response, POST /errors returns a 200 OK if it worked. GET /errors returns a list of error objects. GET /errors/{id} returns the full error details.

For pagination I'd use limit and offset parameters on the GET /errors endpoint. Something like GET /errors?limit=20&offset=0.

I think that covers the main APIs. Should I move on to the data model?"
Fatal Mistakes
  • No versioning — /errors with no version prefix will cause breaking changes on day one
  • Offset-based pagination is explicitly the wrong answer — at billions of rows, OFFSET 1000000 is a full table scan
  • No idempotency key on the write endpoint — SDK retries on network failure = duplicate events
  • No authentication header — how does the system know which project/organization this event belongs to?
  • No error contract — what does a 400 look like? A 429? A 503?
  • POST /errors returns 200 instead of 202 — for async ingestion, 202 Accepted is correct semantics
Interviewer's Notes

"No versioning, wrong pagination strategy, no idempotency, no auth headers, no error contract. The candidate treats APIs as URL stubs rather than contracts. Would not pass L4 bar for a backend role."

LEAN HIRE
Meets L5 bar — not L6
▼
What They Say
"Let me define the core APIs. I'll version them with a /v1/ prefix.

First, the event ingestion endpoint: POST /v1/store. The request body includes: event_id as a UUID for idempotency, timestamp, platform, level, exception object with type, value, and stacktrace frames, breadcrumbs array, tags as key-value pairs, user context, environment, and release fields. The response is 202 Accepted — we're acknowledging receipt asynchronously.

Second, issue listing: GET /v1/issues. Query parameters: project_id, environment, status, cursor for pagination, limit. I'd use cursor-based rather than offset because offset doesn't work at scale. Returns a list of issue summaries with a next_cursor token.

Third, issue detail: GET /v1/issues/{issue_id}. Returns full issue data including event samples, stack trace, tags, user count, event count.

For auth, each SDK authenticates using a DSN — Data Source Name — which is a project-specific token passed in the Authorization header.

For error responses: 400 for bad payload, 401 for invalid DSN, 429 for rate limit exceeded with a Retry-After header."
What's Good
  • Correct versioning with /v1/ prefix
  • Correct pagination choice — cursor-based, not offset
  • Idempotency key present (event_id UUID)
  • Correct HTTP semantics — 202 Accepted for async ingestion
  • DSN-based auth mentioned
  • Structured error responses with correct status codes
What's Missing for L6
  • No rate limiting headers on success responses (X-RateLimit-Remaining, X-RateLimit-Reset)
  • No backward compatibility strategy beyond "versioning"
  • No envelope/batch format — at 100K events/second, per-event HTTP is impractical
  • No compression discussion — stack traces are verbose, gzip/zstd is critical
  • Alert management API missing
  • No idempotency semantics — what happens if same event_id arrives twice?
Upgrade Needed to Reach L6

Add an envelope/batch ingestion format ("at 100K events/second, we cannot afford one HTTP call per event"). Rate limit headers on every response. Explicit idempotency semantics ("duplicate event_id within 24-hour window is silently deduplicated"). A backward compatibility policy ("we never remove fields in v1 — breaking changes require a v2 with a 6-month deprecation window").

HIRE
Meets L6 bar
▼
What They Say
"Let me define the API layer in three groups: the ingestion API used by SDKs, the query API used by the dashboard, and the management API for alert rules.

Ingestion API — POST /v1/envelope
The key design decision here is batching. At 100K events per second, one HTTP round-trip per event is impractical — the network overhead alone would be catastrophic. The SDK batches events into an envelope — a newline-delimited structure with a header line followed by alternating item-header and item-payload lines.

Request headers: Authorization: DSN <dsn_value>, Content-Encoding: gzip (stack traces are verbose, compression is mandatory), X-Sentry-Auth for protocol negotiation.

Response: 202 Accepted with rate limit headers — X-RateLimit-Limit: 1000, X-RateLimit-Remaining: 847, X-RateLimit-Reset: timestamp.

Idempotency: each event carries an event_id UUID generated by the SDK. If the same event_id is received within a 24-hour window, the second occurrence is silently dropped. This handles SDK retries on network failure gracefully.

Query API — GET /v1/projects/{project_id}/issues
Cursor-based pagination, not offset. At billions of events, OFFSET 1000000 forces the database to scan and discard a million rows. A cursor encodes the last seen sort key — typically a composite of (last_seen_at, issue_id) — allowing the query to start exactly where the last page ended via an index seek.

Response includes issues array, next_cursor, prev_cursor, has_more.

Alert Rule Management
POST /v1/projects/{project_id}/alert-rules, GET, PUT, DELETE with soft-delete semantics.

Versioning and Backward Compatibility: URL-versioned with /v1/. Policy: additive changes only within v1 — we never remove or rename fields. Breaking changes require a new /v2/ prefix with a 6-month parallel deprecation window.

Error Contract: All errors return structured JSON with detail, error_code, and retry_after. Status codes: 400 malformed payload, 401 invalid DSN, 413 envelope too large, 429 rate limit with Retry-After, 503 degraded ingestion with Retry-After."

{"event_id":"uuid","timestamp":"...","platform":"python",
