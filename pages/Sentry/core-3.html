High-Level Design

The Interviewer Prompt

"Walk me through the system end-to-end. I want the write path, the read path, your component choices with justification, your consistency model across components, and how this handles users across multiple regions. Weave estimation numbers into your component discussions as you go — not as a separate exercise at the end. Where are your single points of failure? What are your CAP trade-offs?"

NO HIRE
L4 / Weak L5 Signal
▼
What They Say
"Okay so for the high level design, we'll have a few main components. First, the SDKs send errors to our backend. We'll have a load balancer in front to distribute traffic. Then we have an API server that receives the errors and saves them to a database. I'll use PostgreSQL for the database because it's reliable. We should also have a cache — Redis — to make reads faster. And then we have a frontend that queries the API to show the errors.

For the message queue, I'd use Kafka. Kafka is great for high throughput and it's used by a lot of companies. We'll put Kafka between the API server and the database so we can handle spikes in traffic.

For storage, I'd use S3 to store the raw error files. And we can use Elasticsearch for search because it's good at full-text search.

I think that covers the main components. The load balancer distributes traffic, the API servers process events, Kafka buffers the writes, PostgreSQL stores the data, Redis caches reads, S3 stores raw files, and Elasticsearch handles search."
Fatal Mistakes
  • Components listed as a menu, not justified by requirements — "Kafka is used by a lot of companies" is cargo cult reasoning
  • No write path narration — what actually happens to an event from SDK call to durable storage?
  • No read path narration — how does a developer's dashboard query resolve?
  • No estimation woven in — what's the QPS? How many API servers? What's the Kafka partition count?
  • No single point of failure analysis
  • No consistency model discussion
  • No multi-region awareness
  • PostgreSQL for the events store contradicts the 8PB storage math established in Phase 2
  • No deduplication/grouping component — the core feature has no architectural representation
Interviewer's Notes

"Listed components like a shopping list. No write path, no read path, no estimation, no SPOF analysis, no consistency model. Said 'Kafka is used by a lot of companies' — that's not architecture reasoning. PostgreSQL for events after we established 8PB storage requirement shows no connection between requirements and design. Would not advance."

LEAN HIRE
Meets L5 bar — not L6
▼
What They Say
"Let me walk through this end to end — write path first, then read path.

Write path: The SDK calls POST /v1/envelope. This hits a load balancer — I'd use an L7 load balancer like AWS ALB — which routes to one of our ingestion API servers. The API server validates the DSN, checks the project rate limit, and if valid, publishes the envelope to Kafka. We return 202 Accepted immediately. Kafka buffers the events and a consumer group of workers pulls from the queue, processes each event — parses the envelope, normalizes the stack trace, computes the fingerprint, does the upsert to PostgreSQL to find or create the issue — and then writes the event metadata to ClickHouse and the raw payload to S3.

Read path: Developer opens their dashboard, calls GET /v1/projects/{project_id}/issues. This hits the API servers, which query PostgreSQL for the issue list. For popular projects, we'd cache the issue list in Redis with a 30-second TTL. Individual issue detail fetches the issue from PostgreSQL and the latest event sample from ClickHouse.

Key components: AWS ALB, stateless ingestion API servers, Kafka (3 brokers minimum), Event Processing workers, PostgreSQL (issues metadata), ClickHouse (event metadata), S3 (raw payloads), Redis (read cache), Notification service.

Single points of failure: PostgreSQL is a SPOF — I'd add a read replica and use streaming replication for HA. Redis is a SPOF — I'd use Redis Sentinel or Redis Cluster.

Scale estimate: At 100K events/second into Kafka, I'd need at least 100 Kafka partitions — each partition handles about 1,000 events/second at 10KB each, so 100 partitions for 100K events/second."
What's Good
  • Write path and read path narrated clearly
  • Correct async ingestion pattern — Kafka buffer, 202 Accepted
  • Component choices reasonable with some justification
  • SPOF identification for PostgreSQL and Redis
  • Kafka partition math is correct and shows estimation instinct
  • Notification service as a separate component
What's Missing for L6
  • No multi-region discussion — explicitly asked for in the prompt
  • No consistency model across components — what if Kafka consumer fails mid-write?
  • Estimation incomplete — API server count, PostgreSQL sizing, Redis sizing, ClickHouse node count all absent
  • Fingerprinting architecture gap — concurrency challenge not addressed

  • No CAP trade-off discussion — explicitly asked for

Add an explicit CAP trade-off statement by path: "I'm choosing AP on ingestion — during a partition, ingestion nodes continue accepting events; I'm choosing CP on fingerprint-to-issue mapping — I'd rather drop events during a partition than create duplicate issues." Add a multi-region sketch with latency numbers. Add complete inline estimation: "at 100K QPS with 5ms processing, I need 500 concurrent threads — roughly 50 workers at 10 threads each."

"Good write and read path narration. Component choices were reasonable. SPOF identification was present. But no multi-region discussion, no consistency model across components, incomplete estimation, and no CAP trade-off. The fingerprinting architecture gap is significant — that's the hardest part of the design. Lean hire."

HIRE
Meets L6 bar
▼
Opening — Architecture Philosophy
"Let me structure this as: architecture philosophy, write path end-to-end, read path end-to-end, consistency model, multi-region strategy — and I'll weave estimation in as I go.

This system has two fundamentally different traffic patterns that must be isolated from each other. The ingestion path receives 100K events/second and must maintain 99.99% availability — it cannot be degraded by read traffic. The query path serves 2,000 read QPS and can tolerate brief degradation. I'll design these as completely separate service tiers with independent scaling and independent failure domains. A read spike cannot degrade write availability."
Write Path — End to End
1
SDK → Edge (Global LB)
SDK batches events into an envelope, sends POST /v1/envelope. Behind a global load balancer — AWS Route 53 latency-based routing or Cloudflare — routing to the nearest regional ingestion cluster. DNS-based routing adds ~10ms overhead but gets SDKs to the nearest region, critical for our 100ms P99 ingestion SLA.
Latency budget: +10ms
2
Ingestion API Servers (Stateless)
Validate DSN against local LRU cache (no DB hit on hot path), enforce rate limit via Redis token bucket, validate payload size (reject >1MB), publish to Kafka. Return 202. Processing target: 5ms per envelope. At 100K events/second × 0.005s = 500 concurrent threads → 65 ingestion servers (50 cores + 30% headroom), autoscaling at 70% CPU.
65 ingestion servers · 5ms per envelope
3
Kafka Buffer (100 partitions)
At 100K events/second × 10KB = 1GB/second into Kafka. Each partition handles ~50MB/s → 1GB/s ÷ 50MB/s = 20 partitions minimum. Use 100 for headroom. 3 brokers, replication factor 3, min.insync.replicas=2. 7-day retention for replay.
100 partitions · 3 brokers · 1GB/s
4
Event Processor Workers
Consumer group — one thread per partition. Each: parse envelope → normalize stack trace → compute SHA-256 fingerprint → PostgreSQL upsert (ON CONFLICT RETURNING issue_id) → write metadata to ClickHouse → write raw payload to S3 (async) → publish to alert-evaluation topic. Processing target: 10ms per event. 100K events/second × 0.010s = 1,000 concurrent threads → 100 processor servers.
100 processor servers · 10ms per event
5
Alert Evaluation → Notification Dispatch
Alert Evaluator consumes the alert-evaluation topic. Checks alert rules (loaded from local cache, refreshed every 60s) against each event. Deduplicates via Redis. Publishes to notification topic. Notification Dispatcher fans out to Slack, PagerDuty, email with retry + circuit breakers.
Total E2E: 100ms + <1s + 10ms + 20ms + 30ms = ~160ms
Read Path — End to End
1
Query API Tier (Separate from Ingestion)
Completely isolated from ingestion tier — its own load balancer, its own autoscaling group. Reads only. Serves GET /v1/projects/{project_id}/issues.
2
Redis Cache Check
Cache key: (project_id, status, environment, cursor). TTL: 30 seconds. Target cache hit rate: 80%. Cache hit: <50ms response. Cache miss: query PostgreSQL read replica on composite index (project_id, status, last_seen DESC) → <500ms.
80% cache hit rate · 30s TTL
3
Issue Detail + Event Sample
Issue from PostgreSQL. Latest event sample from ClickHouse (SELECT * FROM events WHERE issue_id = ? ORDER BY timestamp DESC LIMIT 1). Full raw payload via pre-signed S3 URL — browser fetches directly from S3, never through our API. Saves ~2MB/s of proxied bandwidth at 2,000 QPS with 10% full-payload requests.
4
Tag-Based Event Search
Routed to ClickHouse for columnar scan with partition pruning. P95 target: <3 seconds per our NFR. Result pages cursor-paginated on (project_id, timestamp).
Explicit CAP Trade-offs by Path
Path / ComponentModelJustification
Ingestion API → KafkaAPDuring a partition, ingestion nodes continue accepting events. May get duplicates — handled by idempotency keys. Availability over consistency.
Fingerprint → Issue mappingCPWould rather the Event Processor retry than create a duplicate issue. PostgreSQL upsert guarantees uniqueness; if PG is unreachable, event stays in Kafka.
Read path (dashboard)Eventually consistentCounts may be 30 seconds stale due to batched Redis flushes. Explicitly acceptable per NFRs.
Alert deduplicationStrong (Redis NX)Must not double-alert on the same issue. Redis SET NX EX 300 — 5-minute dedup window.
SPOF Analysis & Mitigations
  • PostgreSQL — synchronous streaming replication to 1 standby + async to 1 read replica. Patroni automatic failover in ~30 seconds. Event Processors retry via Kafka during failover — no events lost.
  • Kafka — 3-broker cluster, replication factor 3, min.insync.replicas=2. Not a SPOF.
  • Redis — Redis Cluster with 3 primary + 3 replica shards. Loss of one shard degrades cache hit rate temporarily; Query API falls back to PostgreSQL.
  • ClickHouse — 2-shard, 2-replica cluster. Loss of one replica degrades read performance but not data durability.
Multi-Region Strategy
"I'd deploy ingestion clusters in 3 regions — US-East, EU-West, AP-Southeast. SDKs route to nearest region via latency-based DNS. Each regional cluster has its own Kafka and Event Processor fleet. The PostgreSQL instance is global with a primary in US-East and read replicas in EU-West and AP-Southeast — this introduces ~80ms cross-region write latency for fingerprint upserts from EU and AP nodes. That's acceptable given our processing SLA.

The Query API reads from the local read replica in each region — eventual consistency, 2-5 seconds of replication lag. Issue mutations write to the primary and replicate asynchronously. Object storage uses S3 with cross-region replication for durability. ClickHouse is regional — we don't replicate event data cross-region at 1GB/second, that would be prohibitively expensive."

STRONG HIRE
L7 Signal — Exceptional
▼
Opening — Architecture Manifesto
"I want to start with an architecture manifesto before I draw any boxes — the component choices flow from a few non-negotiable principles."
PRINCIPLE 01
The Ingestion Path is Sacred
Must be available even when everything else is degraded. Own failure domain, own scaling group, no synchronous dependencies on anything not also 99.99% available.
PRINCIPLE 02
Loss-Tolerant Ingestion, Loss-Intolerant Grouping
Dropping 0.1% of events is acceptable. Creating duplicate issues for the same error fragments developer attention and degrades the core product.
PRINCIPLE 03
Eventually Consistent Reads — by Design
Developers don't need millisecond-fresh issue counts. Optimize read latency over read freshness. 30-second eventual consistency is acceptable and stated in NFRs.
Layer 1 — Edge & Ingestion
"SDKs send envelopes to a global Anycast IP or Cloudflare routing layer — within ~20ms of origin. At the regional level, NGINX or AWS ALB in front of stateless Ingestion API servers.

Ingestion API responsibilities are deliberately minimal. Authenticate the DSN via local LRU cache (10K DSNs per server, refreshed every 5 minutes — no DB hit on hot path). Enforce rate limits via Redis token bucket (~1ms, one Redis call per envelope). Validate structure and size (reject >1MB). Publish to Kafka with acks=1. That's it. The API server does not touch PostgreSQL. It does not compute fingerprints. It does not make any synchronous call that could be slow.

Why acks=1 instead of acks=all: with acks=all, a Kafka broker failure or slow follower can add 50–200ms to ingestion latency — violating our 100ms P99 SLA. With acks=1, we trade a small durability window for reliable latency. Given raw events are eventually written to S3, this is an acceptable trade-off.

Estimation: 100K events/second. Each envelope averages 5 events at 10KB = 50KB, so 20K envelopes/second. At 5ms per envelope, 100 concurrent threads needed. Each server handles 50 threads → 10 Ingestion API servers with 5x headroom for spikes and rolling deploys."
Layer 2 — Stream Processing (The Key Insight)
"200 Kafka consumer threads matching our 200 partitions — one thread per partition for ordered processing. Partitioned by project_id % num_partitions.

A critical design choice: the Event Processor is the only writer to the issues table. By having ordered, single-threaded processing per project partition, we eliminate the fingerprint race condition for events within the same project. Two events from the same project land on the same Kafka partition, processed sequentially. The only race condition is cross-partition, which is handled by the PostgreSQL upsert. This turns a distributed consistency problem into a local ordering problem — a fundamental simplification that eliminates the need for distributed locks on the hot path.

Each processor: deserialize → normalize stack trace → compute fingerprint (pure local computation, no network calls) → PostgreSQL upsert RETURNING issue_id → batch ClickHouse insert (buffer 1,000 events or 500ms, whichever first — ClickHouse bulk insert is 100x more efficient than row-by-row) → write S3 payload async via dead letter queue → publish (issue_id, is_new_issue) to alert-evaluation topic."
Alert Evaluation — Preventing Alert Storms
"Alert Evaluator consumes from the alert-evaluation topic. For each event batch, loads alert rules from local cache (refreshed every 60s). Evaluates conditions: is_new_issue, error_rate_per_minute via Redis sliding window counter.

If rule fires: deduplicates via Redis — SET alert:{rule_id}:{issue_id} NX EX 300. Don't re-fire the same alert within a 5-minute window. Without this, a 10K events/second incident fires 10,000 Slack messages in one minute, gets us rate-limited by Slack, and causes alert fatigue. The Redis NX pattern is not a nice-to-have — it's a platform stability requirement."
Storage Sizing — Full Stack
  • PostgreSQL — 3TB estimated: 100K issues/day × 90 days × 1KB/issue. Primary + 1 sync replica + 1 async read replica.
  • ClickHouse — 8PB raw → ~800GB after columnar compression at 10:1 ratio. 2 shards × 2 replicas.
  • S3 — 8PB raw payloads, tiered to Glacier after 30 days. Cross-region replication.
  • Redis Cluster — 6 nodes, ~50GB working set: DSN cache + rate limit counters + alert dedup state + issue counter buffers.

Multi-Region — Three Options Compared
"Three regions: US-East (primary), EU-West, AP-Southeast. Ingestion is fully regional — SDKs route via Cloudflare Anycast. Each region has its own Kafka cluster and Event Processor fleet. This means EU events are processed entirely in EU — critical for GDPR data residency.

The hard problem is the PostgreSQL fingerprint upsert across regions. Three options:

Option 1 — Single global PostgreSQL primary in US-East. EU and AP Event Processors make cross-region writes (~80ms latency). Simple, consistent. Processing SLA still met.

Option 2 — Regional PostgreSQL primaries with global issue ID coordination via distributed lock (etcd/Chubby). Complex, high operational burden. Not recommended.

Option 3 — CockroachDB or Google Spanner. Externally consistent, multi-region writes. ~20ms global write latency via Spanner TrueTime. Significant cost increase.

My recommendation: start with Option 1. Accept 80ms cross-region write overhead — Event Processor SLA is still met. Migrate to Spanner if cross-region latency becomes the bottleneck. Don't pay for Spanner until you need it."
Operational Dashboards + Runbook (L7 Signal)
"I'd instrument five key metric dashboards immediately:

1. Ingestion pipeline — events/second by region, P99 acknowledgment latency, Kafka consumer lag by partition
2. Processing pipeline — events processed/second, fingerprint upsert latency P99, PostgreSQL write latency, DLQ depth
3. Storage health — PostgreSQL primary write IOPS, ClickHouse insert queue depth, S3 error rate

On-call runbook for the most common failure — Kafka consumer lag growing: check processor CPU/memory, check PostgreSQL write latency (is the upsert slow?), check if a specific project is flooding (per-project event rate). Fix: scale out Event Processor fleet, or temporarily tighten rate limits to shed load."

🎯 Key Lesson from Phase 4
Close the Loop. Then Derive Elegance from Constraints.

The L5 → L6 shift is about closing the loop between requirements and design: every SLA from Phase 2 should appear as a constraint or calculation in Phase 4. The 60-second alert SLA becomes a 160ms latency budget calculation.

The L6 → L7 shift is about deriving architectural elegance from constraints — the best L7 answers use the system's own constraints (Kafka ordering, partition strategy, upsert atomicity) to solve its hardest problems, eliminating complexity rather than adding it. Before naming any component, state the principle that component serves. That single habit is the most visible L6 signal in Phase 4.

Decision Deep Dive

Stream Processing Architecture

Four approaches compared — when each is right, when each breaks, and the complete decision framework script. Knowing the trade-offs between approaches is an L6/L7 signal that separates candidates who have used Kafka from those who have operated it.

APPROACH 1
Synchronous Processing
Eliminated for This System
Pros
  • Simplest architecture — no queue infrastructure
  • Immediate consistency — issue created before SDK ack
  • Easier to debug — no distributed processing state
Cons
  • 10ms PG upsert + 5ms CH write = 15ms minimum overhead, violates 100ms P99 SLA under load
  • Downstream slowness directly degrades SDK experience
  • Cannot absorb spikes — DB slow during incident = SDK pileup
When it breaks
  • At >10K events/second, DB latency violates ingestion SLA
  • During incidents — 10x volume spike — system degrades exactly when it matters most
APPROACH 2
Kafka-Backed Async Processing
Recommended
Pros
  • Ingestion latency fully decoupled from processing latency
  • Absorbs traffic spikes — Kafka retains messages if consumers slow
  • Replayable — bug in processing? Reprocess from Kafka
  • Independently scalable ingestion and processor fleets
  • Consumer lag is observable and alertable — natural backpressure
Cons
  • Eventual consistency — issue appears 1–2 seconds after SDK call
  • Operational complexity — cluster management, offset management
  • At-least-once semantics require idempotent consumers
  • Consumer lag during incidents may delay alerts (within 60s SLA)
APPROACH 3
Kinesis / Cloud-Managed Streaming
Early-Stage / Cloud-Native
Pros
  • Zero operational overhead for broker management
  • Auto-scaling shards on demand
  • Integrated with cloud ecosystem (Lambda, CloudWatch)
Cons
  • At 100K events/second: 100 shards × $0.015/shard-hour = $1,080/month just in shard capacity
  • No partition-by-project_id with custom partition counts — loses ordering guarantee
  • No exactly-once semantics natively — complex consumer deduplication
  • Pub/Sub: ~100ms latency vs ~10ms for Kafka batch consumers
APPROACH 4
Apache Pulsar
Advanced — Team Expertise Required
Pros
  • Native multi-tenancy — perfect for SaaS model
  • Geo-replication built in — native cross-region topic replication
  • Tiered storage — auto-offloads old messages to S3, reduces cost
  • Separate storage (BookKeeper) and compute (brokers) — scale independently
Cons
  • Higher operational complexity — two separate systems to operate
  • Smaller ecosystem than Kafka — fewer tools, less operational knowledge
  • BookKeeper adds a write path hop — can bottleneck at >500K msg/sec

The Decision Framework Script — 6 Steps
1
State Requirements
"For this system, I need a buffer that provides: decoupled ingestion latency, at-least-once delivery, replayability for reprocessing, and 100K+ QPS throughput."
2
Eliminate
"I can rule out synchronous processing — it couples ingestion latency to DB write latency, a hard no at 100K QPS. I can rule out Pulsar — operational complexity isn't justified without strong geo-replication requirements at the queue layer."
3
Compare Finalists
"Between Kafka and Kinesis: Kafka gives more control — partition count, consumer customization, exactly-once semantics. Kinesis is simpler but at 100K QPS the shard cost becomes significant and we lose partition-by-project_id ordering guarantees."
4
Decide
"Kafka — because we need partition-by-project_id semantics for ordering guarantees, and the team operating at this scale should have Kafka expertise. I'd run on Confluent Cloud or AWS MSK to reduce self-management burden."
5
Acknowledge Trade-off
"Operational complexity — we need dedicated Kafka expertise, partition rebalancing automation, consumer lag monitoring. Mitigate with Confluent Cloud or MSK."
6

"If earlier-stage or cloud-native, I'd start with Kinesis and migrate to Kafka when shard costs exceed $5K/month or when we need custom consumer group semantics."
Complete Strong Hire Script — Stream Processing Decision
"For the ingestion buffer, I need to decouple SDK acknowledgment latency from processing latency — those must be independently controllable. Synchronous processing is immediately eliminated: at 100K QPS, a 10ms PostgreSQL upsert means 10ms minimum ingestion overhead which under load will blow our 100ms P99 SLA.

Between Kafka, Kinesis, and Pulsar: Pulsar is architecturally elegant for multi-tenant geo-replication but the operational complexity — BookKeeper plus brokers — is hard to justify unless we have strong team expertise. I'll set it aside unless we later need native cross-region queue replication.

Between Kafka and Kinesis: at 100K events/second, Kinesis needs 100 shards at $1,080/month just for shard capacity. The more important constraint: Kinesis doesn't give us partition-by-project_id semantics with custom partition counts. I want to partition by project_id so that all events from the same project land on the same partition and are processed in order. This turns the fingerprint race condition — two identical events from the same project creating duplicate issues — into a local ordering problem. Kafka gives me that control explicitly.

So: Kafka with 200 partitions, partitioned by project_id hash. Replication factor 3, min.insync.replicas=2, acks=1 on the producer side — I accept the small durability window of acks=1 over the latency penalty of acks=all. With acks=all and a slow follower, Kafka publish can take 50–200ms — that's most of our 100ms ingestion budget. I'd run on Confluent Cloud or AWS MSK to reduce operational burden while keeping Kafka API semantics.

Migration path: if we add native geo-replication requirements at the queue layer — events from EU must never leave EU before processing — I'd evaluate Pulsar or region-local Kafka clusters with topic mirroring via MirrorMaker 2."
The Non-Obvious L7 Insight

Using Kafka partition ordering as a consistency mechanism. By partitioning events by project_id, all events from the same project land on the same Kafka partition and are processed sequentially by the same consumer thread. For any single project, fingerprint computation and issue upsert happen in strict order — no concurrent fingerprint race within a project. The only race condition is between events from different projects that share a fingerprint (which can't happen since fingerprint includes project_id). This turns a distributed consistency problem into a local ordering problem — eliminating the need for distributed locks on the hot path entirely.
