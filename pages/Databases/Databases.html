1. Database Fundamentals

What is a database really?

At its most fundamental level, a database is a specialized software system designed to solve a single core problem: persistent, structured data management with controlled concurrent access. When we strip away the SQL parser, the fancy query optimizer, and the network protocol handlers, what remains is a storage and retrieval engine that must guarantee that when a client writes data, that data survives process crashes, power failures, and operating system kernel panics, and that when multiple clients attempt to read and write simultaneously, the system behaves predictably.

The "database" abstraction sits at the intersection of three deeply complex computer science domains: storage systems (how bits are laid out on disk and moved to memory), concurrency control (how to schedule overlapping operations without corrupting state), and distributed systems (how to maintain these guarantees when data spans multiple nodes). A database management system (DBMS) is not merely a "bucket for data" — it is a state machine that accepts a stream of operations (transactions), transforms durable storage in a deterministic way, and provides a virtualized, consistent view of that storage to concurrent observers.

When we talk about a "relational database," we are specifically referring to a system that implements the relational model: data is organized into relations (tables), which are sets of tuples (rows) adhering to a schema. The power of this model comes from declarative querying (SQL), where the user specifies what they want, and the system's query planner determines how to retrieve it. This separation of logical and physical data independence is the primary reason relational databases have dominated the industry for four decades.

Storage Engines: B-Tree vs LSM Tree

The storage engine is the beating heart of any database. It determines how data is organized on disk, how writes are buffered, how reads are satisfied, and how the system reclaims space. The two dominant storage engine paradigms are B-Tree engines (used in PostgreSQL, MySQL InnoDB, SQL Server) and Log-Structured Merge Tree (LSM Tree) engines (used in RocksDB, LevelDB, Cassandra, ClickHouse, and underlying systems like Sentry's Snuba).

B-Tree Internals

A B-Tree (specifically a B+Tree in most database implementations) is a self-balancing tree data structure that maintains sorted data and allows searches, sequential access, insertions, and deletions in logarithmic time. The "B" stands for "balanced," and the "plus" in B+Tree indicates that all data records are stored in the leaf nodes, while internal nodes contain only keys for navigation.

In a B+Tree, each node corresponds to a page (or block) on disk, typically sized between 4KB and 16KB. The branching factor (the number of children per node) is determined by the page size and the key size. For example, with 8KB pages and 16-byte keys with 8-byte pointers, a node can hold approximately 340 keys, meaning a tree of height 3 can index over 39 million records with only 3 disk I/Os. This is the mathematical foundation of why B-Trees are so efficient for read-heavy workloads.

When an insertion occurs, the storage engine locates the appropriate leaf node. If the leaf has space, the key is inserted in sorted order. If the leaf is full, a page split occurs: the leaf is divided into two halves, the median key is promoted to the parent internal node, and the two new leaves are linked via a sibling pointer (enabling efficient range scans). Splits can cascade upward if internal nodes are also full, potentially increasing tree height. Conversely, deletions can cause page merges or rebalancing to maintain minimum occupancy thresholds (typically 50%).

The critical characteristic of B-Tree engines is in-place updating. When a row is modified, the storage engine overwrites the existing page on disk. This means B-Trees exhibit read-optimized behavior: point lookups require traversing from root to leaf (3–4 disk seeks), and range scans are extremely efficient due to leaf-node sibling pointers and spatial locality. However, B-Trees suffer from random write amplification: an update to a single row may require writing the leaf page, updating internal node pointers, and eventually flushing the WAL.

LSM Tree Internals

An LSM Tree takes a fundamentally different approach: it treats all writes as append-only operations. When a write arrives, it is first appended to an in-memory structure called a memtable (often a sorted data structure like a skip list or red-black tree). Once the memtable reaches a size threshold (e.g., 64MB), it is frozen and flushed to disk as an immutable, sorted file called an SSTable (Sorted String Table). This flush operation is sequential, meaning it can sustain extremely high write throughput limited primarily by disk bandwidth rather than seek latency.

Because SSTables are immutable, updates to existing keys do not overwrite old data. Instead, a newer version of the key is written to a newer SSTable. Deletes are handled via tombstones — special markers indicating that a key has been removed. This design means that reads may need to check multiple SSTables (newest to oldest) to find the latest version of a key, which is the primary read penalty of LSM Trees.

To prevent read performance from degrading as SSTables accumulate, LSM engines run compaction processes in the background. Compaction merges multiple SSTables, discarding overwritten values and tombstones, and producing new, larger SSTables. There are multiple compaction strategies:

  • Leveled Compaction (LevelDB, RocksDB): SSTables are organized into levels (L0, L1, L2…), where each level is 10x larger than the previous. L0 contains recent flushes and may have overlapping key ranges. L1+ have non-overlapping ranges. Minimizes space amplification but increases write amplification (typically 10–30x).
  • Tiered Compaction (Cassandra, ScyllaDB): Multiple SSTables of similar size are merged together. This reduces write amplification but increases read amplification and space amplification.
  • Time-Window Compaction: Optimized for time-series data, where data is naturally ordered by timestamp and older data is rarely updated.

The trade-off matrix between these engines is central to Staff-level reasoning:

Dimension B-Tree (InnoDB/Postgres) LSM Tree (RocksDB/ClickHouse)

Read Latency (Range)Very Low (sequential leaf scan)Moderate (merge sort across SSTables)
Write ThroughputModerate (random I/O, page splits)Very High (sequential append)

⚙ Sentry Architecture Note

In Sentry's architecture, this trade-off manifests concretely: PostgreSQL (B-Tree) handles metadata, user configurations, and issue states where consistency and complex relational queries matter. ClickHouse (MergeTree engine, LSM-like) powers Snuba, Sentry's analytics platform, where massive write throughput of event data and time-series aggregation are paramount.

ACID Properties and Tradeoffs

ACID is the canonical framework for reasoning about database transaction guarantees, but at the Staff Engineer level, we must understand that ACID is not a binary switch — it is a spectrum of guarantees that come with profound performance and availability trade-offs.

Atomicity

Atomicity ensures that a transaction is treated as a single unit of work: either all operations complete successfully, or none do. The implementation mechanism is the Write-Ahead Log (WAL). Before any data page is modified in memory, the database writes a log record describing the change to a sequential WAL on disk. If the transaction commits, a commit record is appended. If the system crashes before commit, the recovery process reads the WAL and undoes (rolls back) any uncommitted changes. If it crashes after commit but before dirty pages are flushed to data files, the recovery process redoes the committed changes. This undo/redo protocol is the mechanical foundation of atomicity.

Consistency

In the ACID context, consistency means that a transaction brings the database from one valid state to another, preserving all declared integrity constraints (foreign keys, unique constraints, check constraints, triggers). This is distinct from the CAP theorem's consistency or eventual consistency. At scale, strict consistency enforcement becomes expensive: foreign key checks require index lookups on referenced tables, unique constraints require serializable isolation or clever locking, and check constraints must be evaluated for every row affected.

Isolation

Isolation determines how much one transaction can observe the effects of concurrently executing transactions. The SQL standard defines four isolation levels. The core trade-off is: stronger isolation prevents anomalies but requires more locking or multi-version overhead, reducing concurrency and throughput.

Durability

Durability guarantees that once a transaction commits, its effects survive any subsequent failure. The naive implementation is fsync() after every commit — catastrophically slow (milliseconds per transaction). Real databases employ multiple strategies: group commit (batching multiple transactions into a single fsync), asynchronous commit (acknowledging the client before fsync, risking a small window of loss), and write-through caching on battery-backed RAID controllers or NVMe devices with power-loss protection.

🔬 Staff-Level Insight

ACID properties interact antagonistically with distributed systems. In a single-node database, achieving ACID is well-understood engineering. In a sharded, multi-region system, strict ACID requires distributed locking and consensus (2PC, Paxos), which introduces latency penalties and availability risks. This is why modern systems often choose BASE (Basically Available, Soft state, Eventually consistent) for certain data paths while maintaining ACID for critical metadata.

2. Database Indexing Internals

B-Tree Index Internals

We previously discussed B-Trees as storage structures, but indexes are a specific application of B-Trees. A B-Tree index is a secondary access path that allows the database to locate rows without scanning the entire table. The leaf nodes of an index B-Tree contain index entries, each consisting of the indexed column value(s) plus a row pointer (in PostgreSQL, this is a TID — Tuple ID, consisting of block number and offset within the block).

When the query planner decides to use an index, the execution engine performs an index scan: it traverses the B-Tree to find the first matching leaf entry, then follows the row pointer to fetch the actual heap tuple. If the query requires columns not present in the index, this requires a random I/O into the heap, which is expensive. This leads us to covering indexes.

Index maintenance is non-trivial. Every INSERT, UPDATE, or DELETE on the table must maintain all indexes. For a table with 6 indexes, a single row insertion may require 6 B-Tree traversals and potential page splits. This is why excessive indexing hurts write performance.

Page Splits and Fillfactor

PostgreSQL allows specifying a fillfactor (default 90% for tables, 70% for indexes) that leaves space in pages for future updates. A lower fillfactor reduces page splits during heavy update workloads but wastes disk space and increases the tree height, slightly degrading read performance.

Index-Only Scans

PostgreSQL maintains a visibility map — a bitmap indicating which pages contain only tuples visible to all current transactions. When an index-only scan occurs, if all required columns are in the index and the heap page is marked all-visible, the engine can avoid visiting the heap entirely, dramatically reducing I/O.

Clustered vs Non-Clustered Indexes

A clustered index (called "index-organized tables" in Oracle, implemented via CLUSTER or primary key in InnoDB/SQL Server) determines the physical order of rows in the table. In InnoDB, the primary key is a clustered index: the leaf nodes of the primary key B-Tree contain the actual row data, not just pointers. Secondary indexes contain the primary key value as their row pointer, requiring a two-step lookup. This makes primary key lookups extremely fast but means that poor primary key choice (e.g., random UUIDs) causes constant page splits and fragmentation.

A non-clustered index (the default in PostgreSQL) stores the index separately from the heap. The table rows are stored in an unordered heap structure, and indexes provide logical ordering. PostgreSQL's default architecture means there is no "clustered index" in the SQL Server sense, though the CLUSTER command can physically reorder the table to match an index (this is a one-time operation, not maintained).

⚠ Trade-off

Clustered indexes optimize range scans on the primary key and reduce storage overhead, but they make secondary indexes larger and slower, and they penalize random insertions. Non-clustered indexes offer more flexibility but require additional I/O for index-to-heap lookups.

Composite Indexes and Covering Indexes

A composite index (or multi-column index) indexes multiple columns in a specific order: CREATE INDEX idx ON table (a, b, c). The B-Tree sorts entries first by a, then by b within equal a values, then by c. This ordering has strict implications for query usability:

  • A query filtering on a can use the index.
  • A query filtering on a and b can use the index efficiently.
  • A query filtering on a, b, and c can use the index most efficiently.
  • A query filtering on b and c cannot use the index (because the tree is not sorted by b at the top level).
  • A query with a = ? AND c = ? can use the index for a, but c cannot be used for index traversal.

This is the leftmost prefix rule, and violating it is one of the most common causes of index underutilization.

A covering index is an index that contains all columns required by a query. If a query selects a, b, c from a table with a composite index on (a, b, c), and the filter is on a, the database can satisfy the query entirely from the index without touching the heap. This transforms a potentially expensive operation into a pure sequential scan of index leaf pages.

✅ Sentry Application

In high-throughput systems like Sentry, covering indexes are critical for query performance. For example, an issue lookup that filters by project_id and group_id and returns status, priority, last_seen can be satisfied by a covering index on (project_id, group_id, status, priority, last_seen), eliminating heap fetches entirely.

Partial and Expression Indexes

A partial index indexes only a subset of rows that match a predicate: CREATE INDEX idx ON table (col) WHERE status = 'active'. This dramatically reduces index size and maintenance cost when queries predominantly target a subset of data. For example, if 95% of events in an error tracking system are "resolved" and only 5% are "unresolved," but queries almost always look for unresolved issues, a partial index on WHERE status = 'unresolved' is 20x smaller and faster to maintain than a full index.

An expression index indexes the result of an expression rather than raw column values: CREATE INDEX idx ON table (lower(email)). This allows efficient case-insensitive lookups. Expression indexes require exact expression matching — the query must use the identical expression lower(email) to utilize the index.

⚙ Staff-Level Signal

Partial indexes demonstrate deep understanding of workload characteristics: they are a form of co-designing the database schema with the application query patterns, which is exactly what separates senior engineers from staff engineers.

3. Query Execution

SQL Parsing and Planning

When a SQL statement arrives at the database, it undergoes a multi-stage pipeline before execution:

  1. Parsing: The raw SQL string is tokenized and parsed into a parse tree. This stage checks syntactic correctness but knows nothing about table existence or column types.
  2. Semantic Analysis: The parser tree is transformed into a query tree by resolving table names, column names, data types, and verifying permissions. This produces a logical representation of the query.
  3. Rewriting: The query tree is rewritten by the rule system (in PostgreSQL, this includes view expansion, rule evaluation, and preliminary optimization). Subqueries may be flattened, views are expanded to their base definitions.
  4. Planning: The rewritten query is handed to the query planner/optimizer, which generates multiple candidate execution plans and selects the cheapest one.

The planner operates on relational algebra — it transforms the logical query (what to retrieve) into a physical plan (how to retrieve it). A complex query with multiple joins, filters, and aggregates may have thousands or millions of possible execution plans. The planner uses dynamic programming (specifically, the Selinger-style algorithm for join ordering) to find a good plan without exhaustive enumeration.

Cost-Based Optimization

Cost-based optimization (CBO) is the art of estimating the "cost" of each operation in a plan, where cost is an abstract unit representing a combination of I/O operations, CPU cycles, and memory usage. The optimizer relies heavily on statistics stored in the system catalog:

  • Table cardinality: Estimated number of rows.
  • Column statistics: Most common values, histograms of value distributions, correlation between physical ordering and logical ordering, fraction of nulls.
  • Index statistics: Tree height, number of leaf pages, index correlation.

The cost model is parameterized by constants like seq_page_cost (default 1.0), random_page_cost (default 4.0), cpu_tuple_cost, and cpu_index_tuple_cost. These can be tuned for different storage media — for example, lowering random_page_cost to ~1.1 for SSDs, as random reads are nearly as fast as sequential reads on flash storage.

⚠ Critical Warning

Statistics become stale. As data is modified, the distribution shifts. If the planner thinks a table has 1,000 rows but it actually has 10,000,000, it may choose a nested loop join when a hash join would be vastly superior. This is why ANALYZE (statistics refresh) is crucial, and why auto-vacuum/auto-analyze policies must be carefully tuned.

Join Algorithms

Joins are among the most expensive operations in relational databases. The three fundamental algorithms are:

Nested Loop Join

The simplest algorithm: for each row in the outer (left) table, scan the inner (right) table for matches. Complexity is O(M × N). This is only efficient when the outer table is tiny, or when the inner table has an index on the join key (reducing the inner scan to O(log N) per outer row). Nested loops are the default choice for small datasets and are essential for index-sensitive joins where one table is filtered down to a handful of rows.

Hash Join

The database builds an in-memory hash table from the smaller relation on the join key, then scans the larger relation, probing the hash table for each row. Average complexity is O(M + N). Hash joins require sufficient memory to hold the hash table (or spill to disk via recursive partitioning if memory is insufficient). They are unbeatable for large, unindexed tables with equality join conditions. However, they fail for non-equality conditions (range joins).

Merge Join

Both tables are sorted on the join key (or indexes providing sorted output are used), then a synchronized scan walks through both sorted streams, emitting matches. Complexity is O(M log M + N log N) for sorting, or O(M + N) if pre-sorted. Merge joins excel when both inputs are large and already sorted, and when the join condition includes range comparisons.

🔬 Staff-Level Note on Join Ordering

For a query joining 5 tables, the order matters enormously. A poor order might process billions of intermediate rows, while an optimal order keeps intermediate results small. The planner uses heuristics and cost estimation to determine this, but complex queries with correlated subqueries or non-uniform distributions can defeat the optimizer, necessitating manual hints or query restructuring.

Execution Models and EXPLAIN ANALYZE

Database execution engines typically implement one of two models:

  • Iterator Model (Volcano/Pipeline): Each operator implements a next() method. The top-level operator calls next() on its child, creating a demand-driven pipeline. This is memory-efficient (no need to materialize intermediate results) but can have high function-call overhead.
  • Vectorized Execution: Operators process batches of rows (e.g., 1,000 rows at a time) using compact columnar representations. This amortizes interpretation overhead and enables SIMD CPU instructions. Vectorization is used in modern analytical databases (ClickHouse, DuckDB, Snowflake) and is why Sentry's Snuba platform can aggregate billions of events in seconds.

EXPLAIN ANALYZE is the definitive tool for understanding query execution. It outputs the actual plan tree with actual row counts, actual execution time, and loop counts, alongside the planner's estimates. The critical analysis technique is to look for:

  • Discrepancies between estimated and actual rows (indicating stale statistics)
  • Sequential scans on large tables (missing indexes)
  • High-cost nested loops (suggesting hash join might be better)
  • Memory spills (indicating work_mem is too small)

4. Pagination

OFFSET/LIMIT Internals

The traditional pagination approach is SELECT * FROM table ORDER BY id LIMIT 10 OFFSET 1000. While this appears simple, its performance characteristics are catastrophic at scale. To return 10 rows starting at offset 1000, the database must:

  1. Scan the index (or table) in sorted order.
  2. Fetch and discard the first 1000 rows.
  3. Return rows 1001–1010.

The database still performs the I/O and CPU work to retrieve those 1000 discarded rows. As offset grows to millions, query latency grows linearly. At offset 10,000,000, the database may need to process tens of millions of rows just to return a single page of 20 results. This is O(n) complexity where n is the offset.

Furthermore, OFFSET/LIMIT is unstable under concurrent modifications. If a new row is inserted between page requests, the entire offset window shifts, causing rows to be skipped or duplicated across pages.

Keyset Pagination

Keyset pagination (also called "cursor pagination" or "seek method") solves both problems by encoding the position in the data itself. Instead of an offset, the query uses the last seen value of the ordering column:

SQL 
SELECT * FROM table 
WHERE (created_at, id) > ('2026-05-01 12:00:00', 12345) 
ORDER BY created_at, id 
LIMIT 10;

This leverages the index to seek directly to the starting position, then scan forward for 10 rows. Complexity is O(log n + page_size) — the index seek is logarithmic, and the scan is proportional to the page. Even at billion-row scale, retrieving the next page takes milliseconds.

Keyset pagination requires a unique, immutable ordering key (or composite key ensuring uniqueness). It is stable under inserts (new rows simply appear in future pages) and is the only viable pagination method for large-scale systems.

The trade-off is that it does not support jumping to arbitrary pages (e.g., "go to page 50") without encoding and storing cursors, and it complicates backward navigation.

Distributed Pagination Challenges

In a sharded system, pagination becomes significantly harder. If data is partitioned across 100 shards, a global ORDER BY with LIMIT 10 requires:

  1. Sending the query to all 100 shards.
  2. Each shard returns its top 10 results.
  3. The coordinator merges 1000 results, re-sorts, and takes the global top 10.

This is the scatter-gather pattern, and it scales poorly. For page 1000 (offset 10,000), the coordinator might need to retrieve and sort 1,000,000 rows from shards. This is why distributed systems often:

  • Avoid deep pagination entirely (e.g., Google Search stops at ~1000 results)
  • Use sorted indexes with locality (e.g., partition by time so recent queries hit only recent shards)
  • Implement approximate pagination (acceptable for analytics, unacceptable for billing)
✅ Sentry Application

In Sentry's context, when displaying the "latest 20 issues" across a multi-region deployment, keyset pagination on (last_seen, group_id) is essential. The system cannot afford to OFFSET through millions of historical issues.

5. Partitioning and Sharding

Range, Hash, and List Partitioning

Partitioning splits a single logical table into multiple physical chunks within one database instance, managed by the DBMS. Sharding distributes partitions across multiple independent database instances. Both aim to reduce the working set size per chunk, enabling parallel operations and manageable maintenance windows.

Range Partitioning

Rows are partitioned by ranges of a column (typically time). For example, an events table might have partitions events_2026_01, events_2026_02. Range partitioning is ideal for time-series data because it naturally supports data lifecycle management (dropping old partitions is instant metadata operations, not massive DELETEs), and queries filtering by time can achieve partition pruning — the planner only scans relevant partitions.

Hash Partitioning

A hash function on the partition key determines the partition. This distributes data uniformly, eliminating hot spots from sequential keys. However, it complicates range queries (they must scan all partitions), and rebalancing requires moving data when the modulus changes.

List Partitioning

Explicitly maps discrete values to partitions (e.g., partition by region or status). This is useful when the domain is small and known.

Shard Key Selection

Choosing a shard key is one of the most consequential decisions in distributed database design. The ideal shard key:

  • Has high cardinality (many distinct values) to distribute load evenly.
  • Is immutable (changing it requires moving the row).
  • Provides query locality (queries typically filter or join on it, allowing shard targeting).
  • Avoids hot spots (sequential keys like timestamps can concentrate write load on the "latest" shard).

In Sentry, event data is sharded by project_id or organization_id. This provides locality (users query within their projects) and distributes load. However, a viral project can create a hot shard, overwhelming one node. Mitigations include:

  • Hashing within the project (sub-sharding by event_id)
  • Rebalancing (moving hot shards to dedicated nodes)
  • Rate limiting at ingestion (Sentry's Relay enforces per-project quotas)

Rebalancing Strategies

Rebalancing moves data when shards grow unevenly or nodes are added/removed:

Consistent Hashing

Maps both data and nodes to a ring. Adding/removing a node only affects adjacent ranges, minimizing data movement. Used in DynamoDB, Cassandra, and Riak. The trade-off is that load balancing is approximate and requires virtual nodes (vnodes) to smooth distribution.

Range-Based Rebalancing

The coordinator maintains a directory mapping key ranges to nodes. It can split hot ranges and migrate them. This is used in Spanner, CockroachDB, and HBase. It provides precise control but requires a centralized metadata service (a potential bottleneck and single point of failure).

Online Rebalancing

Modern systems support live migration — copying data to a new node while serving reads/writes from the old node, then atomically switching. This requires logical replication or change data capture (CDC) to stream ongoing changes during the bulk copy.

⚙ Staff-Level Note

Rebalancing is not just a technical problem but an operational and business problem: it requires maintenance windows (or online migration), impacts latency during data transfer, and may violate consistency guarantees if not carefully orchestrated.

6. Distributed Transactions

2PC Internals

Two-Phase Commit (2PC) is the classic algorithm for achieving atomic commitment across multiple nodes. It involves a coordinator and multiple participants:

Phase 1 (Voting)

  1. The coordinator writes a prepare record to its durable log.
  2. The coordinator sends PREPARE messages to all participants.
  3. Each participant receives the message, forces all transaction changes to its local WAL (making them durable), acquires necessary locks, and replies YES (prepared successfully) or NO (failed).

Phase 2 (Commit/Abort)

  1. If all participants voted YES, the coordinator writes a commit record and sends COMMIT messages.
  2. If any participant voted NO, the coordinator writes an abort record and sends ABORT messages.
  3. Participants acknowledge receipt and release locks.
⚠ 2PC Fatal Flaw

Once a participant votes YES, it is bound to commit or abort based on the coordinator's decision. If the coordinator crashes after sending PREPARE but before completing Phase 2, participants holding locks must wait for the coordinator to recover. This blocking window during coordinator failure is 2PC's fundamental limitation.

Recovery Scenarios

  • If the coordinator crashes before sending PREPARE, it aborts on recovery.
  • If it crashes after receiving all votes but before sending decisions, it reads its log on recovery and re-sends the decisions.
  • If a participant crashes and recovers, it examines its log: if it has a PREPARED record but no final decision, it contacts the coordinator to learn the outcome (or blocks if the coordinator is down).

3PC Tradeoffs

Three-Phase Commit attempts to solve 2PC's blocking problem by adding an additional phase:

  1. Phase 1: CanCommit? (Coordinator asks participants if they are able to commit — no durable writes yet)
  2. Phase 2: PreCommit (Coordinator sends pre-commit; participants acknowledge and write to WAL)
  3. Phase 3: DoCommit (Coordinator sends final commit)

3PC assumes synchronous communication and bounded network delays — assumptions that violate the asynchronous system model of real distributed systems. In practice, 3PC is rarely used because:

  • It doubles message latency (three round-trips vs. two).
  • It does not actually solve blocking under real network partitions (the FLP impossibility result shows consensus is impossible in asynchronous systems with even one faulty process).
  • It adds complexity without practical reliability gains.

Saga Pattern

The Saga pattern accepts that ACID across distributed services is often infeasible and instead models a long-lived transaction as a sequence of local transactions, each with a compensating transaction to undo its effects if the saga fails.

For example, in an e-commerce system:

  • T1: Reserve payment → C1: Refund payment
  • T2: Create order → C2: Cancel order
  • T3: Reserve inventory → C3: Release inventory

If T3 fails, the saga executes C2 and C1, rolling back the prior steps. Sagas are eventually consistent and require the application to handle intermediate states. They are the dominant pattern in microservices architecture because they avoid distributed locking and coordinator bottlenecks.

Saga Implementations

  • Choreography: Each service emits events that trigger the next step. Decentralized but harder to trace.
  • Orchestration: A central saga manager coordinates steps. Easier to monitor but introduces a single point of failure.
✅ Sentry Application

In Sentry's context, a user deletion saga might need to: delete from PostgreSQL, delete from ClickHouse, remove from Redis, and purge from object storage. Each step has a compensating action, and the system must handle partial failures gracefully.

Consensus-Based Approaches

Modern distributed databases (Spanner, CockroachDB, TiDB) use consensus algorithms (Paxos, Raft) to replicate transaction logs across nodes. Rather than 2PC across independent databases, they maintain a replicated state machine where all nodes in a shard process the same transaction log in the same order.

Raft (the more understandable alternative to Paxos) elects a leader that accepts writes, appends them to its log, and replicates them to followers. A write is committed once a majority of nodes acknowledge it. If the leader fails, a new leader is elected from nodes with the most up-to-date log.

This provides linearizability (strong consistency) within a shard without the blocking problems of 2PC, because the "coordinator" (leader) is itself a replicated entity that can fail over. The trade-off is latency: writes require round-trips to a majority, making cross-region consensus slow (typically 100–500ms depending on distance).

7. Locking and Concurrency Control

Lock Types and Granularity

Databases implement multiple lock types to balance concurrency with correctness:

Lock Type Description Compatibility
Shared (S-lock)Acquired for readsCompatible with other S-locks
Exclusive (X-lock)Acquired for writesIncompatible with S-locks and other X-locks
Intent LocksHierarchical — signals finer-grained locks exist belowPrevents conflicting table-level locks
Update LocksHybrid between S and X, used for SELECT FOR UPDATEPrevents deadlock on read-then-upgrade pattern

Lock Granularity ranges from coarse (table locks, cheap to acquire but low concurrency) to fine (row locks, expensive to manage but high concurrency). Modern databases use lock escalation (promoting many row locks to a single table lock when row lock overhead becomes excessive) and latches (lightweight in-memory locks protecting internal data structures like buffer pool pages, distinct from transaction locks).

MVCC Internals

Multi-Version Concurrency Control is the mechanism that allows readers to not block writers and writers to not block readers. Instead of locking rows, the database maintains multiple versions of each row, each tagged with the transaction ID (XID) that created it.

PostgreSQL's MVCC Implementation

  • Every row has system columns xmin (transaction ID that inserted the row) and xmax (transaction ID that deleted/updated it; 0 if live).
  • Every transaction gets a snapshot at its start, recording the current XID counter and the set of active transactions.
  • When a transaction reads a row, it checks visibility: the row is visible if xmin is committed before the snapshot and xmax is either 0 or a transaction that aborted or committed after the snapshot.
  • When a transaction updates a row, it does not overwrite the existing tuple. Instead, it creates a new tuple version with xmin = current XID and sets xmax of the old tuple.

This means UPDATE is effectively DELETE + INSERT at the storage layer. The old versions become "dead tuples" that must be reclaimed by VACUUM. MVCC eliminates read locks entirely but introduces storage overhead (multiple versions) and cleanup overhead (vacuuming).

Isolation Levels

The SQL standard defines four isolation levels based on which phenomena are permitted:

Level Dirty Read Non-Repeatable Phantom Write Skew Implementation Cost
Read UncommittedYesYesYesYesNone
Read CommittedNoYesYesYesLow
Repeatable ReadNoNoSometimesYesMedium
SerializableNoNoNoNoHigh (aborts)

Level Descriptions

  • READ UNCOMMITTED: Transactions may read changes made by concurrent transactions before they commit (dirty reads). Rarely used in practice.
  • READ COMMITTED: A transaction sees only committed data. However, executing the same query twice may yield different results. This is the default in PostgreSQL.
  • REPEATABLE READ: A transaction sees a consistent snapshot as of its start time. Re-executing the same query always yields the same results.
  • SERIALIZABLE: The highest level, guaranteeing that concurrent transactions execute as if serialized. PostgreSQL implements this via Serializable Snapshot Isolation (SSI), which detects serialization conflicts and aborts one transaction.
⚙ Staff-Level Insight

Most OLTP systems run on READ COMMITTED and handle consistency at the application level (optimistic locking, idempotency keys) because SERIALIZABLE is often 2–10x slower and experiences high abort rates under contention.

Deadlock Handling

Deadlocks occur when two or more transactions wait indefinitely for each other's locks. For example:

  • T1 locks row A, requests row B.
  • T2 locks row B, requests row A.

Databases detect deadlocks via wait-for graphs — directed graphs where nodes are transactions and edges represent lock waits. If a cycle is detected, the database selects a victim transaction (typically the one with the least work invested) and aborts it. The client must retry.

Prevention strategies include:

  • Lock ordering: Always acquire locks in a global order (e.g., by primary key). This eliminates cycles but requires application discipline.
  • Timeouts: Abort transactions waiting longer than a threshold. Simple but may abort transactions unnecessarily.
  • Pre-declaration: Acquire all needed locks at the start. Rarely practical for complex transactions.

8. Additional Staff-Level Topics

WAL and Crash Recovery

The Write-Ahead Log is the fundamental mechanism ensuring durability and atomicity. All modifications are written to an append-only log before being applied to data pages. The WAL is organized into records, each with a Log Sequence Number (LSN).

Checkpointing

Periodically, the database performs a checkpoint, flushing all dirty data pages to disk and recording the checkpoint LSN. After a crash, recovery starts from the last checkpoint LSN and replays WAL records (redoing committed transactions and undoing uncommitted ones). Checkpoints must balance frequency: frequent checkpoints reduce recovery time but increase I/O load; infrequent checkpoints risk long recovery times.

Full Page Writes

In PostgreSQL, during the first modification of a page after a checkpoint, the entire page image is written to the WAL. This protects against torn pages — partial writes that can occur if the OS crashes while writing an 8KB page (since disk sectors are typically 512 bytes or 4KB). This doubles WAL volume during heavy write loads but is essential for crash safety on non-atomic storage.

Replication

Physical Replication (Streaming Replication)

The primary node ships WAL records to standbys, which apply them byte-for-byte. This creates an exact binary copy. Synchronous replication waits for at least one standby to acknowledge writes before committing, providing RPO=0 (zero data loss) at the cost of write latency. Asynchronous replication acknowledges immediately, maximizing performance but risking data loss on primary failure.

Logical Replication

Decodes WAL records into logical changes (row inserts/updates/deletes) and streams them. This allows replication between different versions, selective table replication, and replication to non-PostgreSQL targets. It operates at the row level and can handle conflicts.

Replication Lag

Standbys may fall behind during heavy write loads. Lag is measured in bytes (WAL lag) or time. Applications must handle lag by routing reads to the primary when fresh data is required, or accepting stale reads from standbys.

Connection Pooling

Database connections are expensive (processes or threads, memory allocation, catalog caching). At scale, direct per-client connections exhaust database resources. Connection pooling (via PgBouncer, RDS Proxy, or application pools) multiplexes many client connections over fewer database connections.

ModeAssignmentSharingBreaks
Session poolingClient gets dedicated backend for entire sessionLowNothing
Transaction poolingBackend assigned per transaction, then returnedHighPrepared statements, advisory locks, SET
Statement poolingRotating backends per statementExtremeMost session semantics

At Staff level, transaction pooling is usually preferred for stateless application servers, but requires careful application design (no session state in the database).

Vacuum and Bloat

In PostgreSQL, UPDATE and DELETE do not immediately reclaim space. They leave dead tuples that accumulate as bloat — wasted space in tables and indexes. The autovacuum daemon scans tables, marks dead tuples as reusable space in the free space map (FSM), and updates visibility maps.

If autovacuum cannot keep up (e.g., massive bulk loads, long-running transactions holding back the cleanup horizon), bloat grows indefinitely, degrading performance and wasting storage. Manual intervention (VACUUM FULL, which rewrites the table exclusively, or pg_repack for online rewriting) becomes necessary.

⚠ Transaction ID Wraparound

PostgreSQL uses 32-bit transaction IDs that wrap around after ~2 billion. If a table is not vacuumed before wraparound, the database must shut down to prevent data loss. This is a critical operational monitoring metric: age(datfrozenxid).

9. Staff-Level Interview Questions

UUID vs Sequential PKs

Sequential primary keys (BIGINT, auto-increment) provide locality: new rows are appended at the end of the table, minimizing page splits and maximizing cache locality. They are compact (8 bytes) and efficient for indexing. However, they leak insertion rates (competitors can estimate your growth), complicate multi-master replication (sequence conflicts), and create hot spots in distributed systems (all writes go to the "latest" shard).

UUIDv4 (random) eliminates hot spots and leakage but causes severe index fragmentation: every insertion hits a random page in the B-Tree, causing constant page splits, low fillfactor, and poor cache locality. Index sizes can grow 2–3x larger than sequential keys.

UUIDv7 (recently standardized) combines the best of both: the first 48 bits are a Unix timestamp (millisecond precision), followed by random bits. This provides time-ordering (locality) while retaining uniqueness and privacy. For Sentry's event storage, UUIDv7 would provide better insertion locality than random UUIDs while avoiding the distributed coordination of sequences. The trade-off is storage size: UUIDs are 16 bytes vs. 8 bytes for BIGINT, doubling index size and reducing cache effectiveness.

Hash Join vs Nested Loop

The interview nuance is: given a query joining a 10-row table to a 10-million-row table, the optimal plan is a nested loop with an index on the large table (10 index lookups). A hash join would require scanning and hashing the 10-million-row table, which is catastrophically worse. The Staff Engineer must demonstrate that algorithm choice is data-dependent, not rule-based.

MVCC Explanation

The candidate should explain tuple versioning, snapshot acquisition, visibility rules, and the cleanup problem (dead tuples, vacuum). They should contrast PostgreSQL's approach (dead tuples in heap, vacuum cleanup) with InnoDB's (undo log in rollback segments, background purge).

Write Skew

Write skew is the anomaly that occurs under snapshot isolation (REPEATABLE READ). Two transactions read the same data, make disjoint modifications based on what they read, and both commit. Individually, each transaction is consistent, but together they violate a constraint.

Classic Example: Hospital On-Call

A hospital requires at least one doctor on call. Two doctors, Alice and Bob, are on call. Both simultaneously check and see the other is on call. Both decide to go off call. Both commit. Now no one is on call.

Serializable isolation prevents this via SSI. At the application level, it can be prevented by using SELECT FOR UPDATE or by materializing the constraint (e.g., updating a dummy row that both transactions must lock).

Pagination Tradeoffs

OFFSET/LIMIT is simple but O(n) and unstable. Keyset pagination is O(log n) and stable but cannot jump to arbitrary pages and requires immutable ordering. In distributed systems, deep pagination requires scatter-gather and is often prohibitive. The correct answer is usually: "We use keyset pagination for production APIs, restrict deep pagination in UI, and use pre-aggregated counters or search indexes for analytics pagination."

10. Quick Reference Cheat Sheet

Index Selection Guide

  • High-cardinality equality filters: B-Tree index.
  • Range queries: B-Tree index on the range column.
  • Text search: GIN (Generalized Inverted Index) for PostgreSQL full-text search, or specialized engines (Elasticsearch).
  • JSONB containment: GIN index with jsonb_path_ops.
  • Geospatial: GiST or SP-GiST indexes.
  • Write-heavy, read-light: Minimize indexes; consider partial indexes for critical queries.
  • Covering queries: Include all selected columns in the index (INCLUDE clause in PostgreSQL 11+).

Performance Tuning Priorities

  1. Schema & Queries: Proper data types, avoid N+1 queries, use covering indexes.
  2. Connection Management: Pool size ≈ (core_count * 2) + effective_spindle_count; use transaction pooling.
  3. Memory: shared_buffers (typically 25% of RAM); work_mem (per-operation sort/hash memory; too high causes swapping, too low causes disk spills).
  4. Storage: SSD/NVMe for random I/O; tune random_page_cost to 1.1 for SSDs.
  5. Concurrency: Tune autovacuum aggressiveness; monitor lock waits and deadlocks.
  6. Replication: Use read replicas for analytical queries; monitor replication lag.

Requirements & API Design

Functional Requirements

An error tracking system must accept events (errors, exceptions, transactions, replays) from client SDKs, process them into issues (grouped occurrences of the same error), and provide a web UI and API for developers to query, triage, and resolve these issues.

The core entities are:

  • Event submission: POST /api/{project_id}/store/ with a JSON payload.
  • Envelope protocol: A structured format supporting multiple items (events, attachments, sessions) in one request, with chunked transfer encoding for large payloads.
  • DSN (Data Source Name): A URL containing the project public key, used for authentication and routing.

Pillar 2
Event Ingestion & Stream Processing
2

Architecture: Relay, Kafka, and Consumers

Sentry's ingestion architecture follows the edge-buffer-core pattern:

Edge Layer (Relay)

Relay is Sentry's edge proxy, written in Rust. It runs in multiple regions close to clients. Its responsibilities are:

  • Authentication: Validates the DSN (public key) and project configuration.
  • Rate Limiting: Enforces per-project quotas using a token bucket algorithm backed by Redis.
  • PII Scrubbing: Applies data scrubbing rules (regex-based) to remove sensitive information (passwords, credit cards, tokens) before events enter the core infrastructure.
  • Normalization: Validates JSON schema, normalizes timestamps, enforces size limits (e.g., stack traces truncated to 250 frames), and extracts metrics.
  • Batched Writes: Buffers events and writes them to Kafka in batches for efficiency.

Relay is stateless and horizontally scalable. It uses backpressure — if Kafka is slow, Relay stops reading from clients, causing their TCP buffers to fill and naturally slowing them down.

Buffer Layer (Kafka)

Apache Kafka acts as the durable, replicated buffer between ingestion and processing. Events are written to a topic (e.g., ingest-events) with partitioning by project_id (ensuring per-project ordering). Kafka provides:

  • Durability: Events are replicated across 3 brokers before Relay acknowledges the client.
  • Decoupling: The ingestion rate and processing rate can differ temporarily.
  • Replay: If downstream processors have bugs, they can be rewound and replayed from Kafka.

The choice of Kafka over a simple queue (RabbitMQ, SQS) is deliberate: Kafka's log-based model provides higher throughput, better retention, and consumer group semantics that allow multiple independent consumer groups to read the same stream.

Processing Layer (Consumers)

Multiple consumer groups read from Kafka:

  • Event Consumer: Deserializes events, runs grouping algorithms, writes event data to object storage and metadata to PostgreSQL/ClickHouse.
  • Post-Process Consumer: Handles issue state transitions (new issue, regression, resolved), triggers alerts, and updates search indexes.
  • Metrics Consumer: Extracts span metrics, trace metrics, and custom metrics into time-series storage.
  • Attachment Consumer: Handles large files (replays, profiles) uploaded alongside events.

Grouping Algorithm

Grouping is the process of converting an event into an issue fingerprint. This is a deterministic hash of normalized attributes:

  • For exceptions: the exception type, stripped stack trace (module names, function names, line numbers; but not absolute file paths).
  • For transactions: the transaction name and op-code.

The algorithm must be stable (the same error always groups to the same issue) but adaptable (if a code change shifts line numbers, the issue should not fragment). Sentry uses multiple strategies: legacy grouping by stack trace, "new" grouping by in-app frames only, and AI-powered dynamic grouping that uses machine learning to cluster similar-looking issues.

Stream Processing Trade-offs

Ordering vs. Parallelism

Kafka partitions provide per-project ordering, but global ordering is impossible at scale. Two events for the same issue arriving on different partitions may temporarily have inconsistent counters until asynchronous reconciliation.

Exactly-Once Semantics

Kafka supports exactly-once delivery via idempotent producers and transactional consumers. Sentry opts for at-least-once delivery with idempotent writes (upserts on event ID) because 2PC across Kafka and PostgreSQL would introduce unacceptable latency.

Schema Evolution

The event schema evolves constantly as SDKs add new fields. The processing layer uses a schema registry to enforce backward and forward compatibility. Unknown fields are passed through opaquely to prevent data loss.

Hot Partition Problem

Partitioning by project_id means a viral project can create a hot partition. Mitigation: large number of partitions (thousands) to reduce hot spot probability, or sub-partitioning by event_id within a project.

The Dual-Storage Strategy

Sentry employs a polyglot persistence architecture, which is the correct Staff-level answer for any system with heterogeneous access patterns:

PostgreSQL Schema Deep Dive

The core tables demonstrate advanced relational modeling:

  • sentry_project: Project metadata, DSN configuration, grouping settings.
  • sentry_groupedmessage (the "Issue" table): Contains status, priority, times_seen, last_seen, first_seen, score. This table is heavily contended.
  • sentry_eventmapping: Maps event IDs to group IDs and project IDs.
  • sentry_userreport: User feedback linked to issues.

The sentry_groupedmessage table illustrates the write hotspot problem: a viral issue receiving 10,000 events/second causes constant updates to the same row. PostgreSQL's row-level locking means these updates serialize. Sentry mitigates this by:

  • Counter buffering in Redis (per-issue counters with 10-second TTL)
  • Batch updates: flushing to PostgreSQL every 5 seconds via UPDATE ... SET times_seen = times_seen + 50
  • Advisory locks to serialize flushes per group ID

ClickHouse / Snuba Deep Dive

ClickHouse is a columnar OLAP database using the MergeTree engine family (an LSM-Tree variant optimized for time-series). Data is partitioned by time and ordered by a primary key (typically (project_id, timestamp, event_id)).

MergeTree Mechanics

  • Data is stored in parts — immutable, compressed column files.
  • Background merges combine smaller parts into larger ones, applying sort order and compression.
  • ReplacingMergeTree is used for event data: if the same event ID is written twice (e.g., retry), the merge process eventually keeps only the latest version.
SQL — ClickHouse Schema 
CREATE TABLE events (
    project_id UInt64,
    timestamp  DateTime64(6),
    event_id   UUID,
    group_id   UInt64,
    platform   LowCardinality(String),
    level      LowCardinality(String),
    tags       Nested(key String, value String),
    message    String,
    -- ... many columns
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)
ORDER BY (project_id, timestamp, event_id);

The ORDER BY clause is critical: it determines the physical sort order on disk. Queries filtering by project_id and timestamp achieve excellent pruning and cache locality. The PARTITION BY clause enables dropping old data (ALTER TABLE ... DROP PARTITION) instantly.

Pillar 4
Query Execution & Retrieval Systems
4

The Query Problem

Sentry faces a dual query load:

  • OLTP Queries: "Show me the 20 unresolved issues for project X, sorted by last seen." These hit PostgreSQL.
  • OLAP Queries: "Show me the error rate for my API over the last 24 hours, broken down by release." These hit Snuba/ClickHouse.

PostgreSQL Query Path

SQL — Issue List Query 
SELECT g.id, g.status, g.priority, g.times_seen, g.last_seen
FROM sentry_groupedmessage g
WHERE g.project_id = 123 
  AND g.status = 0  -- unresolved
ORDER BY g.last_seen DESC
LIMIT 20;

This requires a composite index on (project_id, status, last_seen DESC) or, better, a covering index including priority and times_seen to avoid heap fetches. However, with millions of issues per project, even index scans become heavy. This is why partial indexes are powerful:

SQL — Partial Index 
CREATE INDEX idx_unresolved ON sentry_groupedmessage (project_id, last_seen DESC) 
WHERE status = 0;

ClickHouse / Snuba Query Path

SQL — Snuba Analytical Query 
SELECT 
    toStartOfFiveMinute(timestamp) as bucket,
    countIf(level = 'error') / count() as error_rate,
    uniq(user) as affected_users
FROM events
WHERE project_id = 123 
  AND timestamp >= now() - INTERVAL 24 HOUR
GROUP BY bucket
ORDER BY bucket;

ClickHouse executes this using vectorized processing: it reads compressed column blocks, applies predicates using SIMD instructions, and aggregates in memory. The countIf and uniq (approximate distinct count via HyperLogLog) are native, highly optimized functions.

Caching Strategy

Query results are cached in Redis with TTLs based on data freshness:

  • Real-time dashboards: 5-second TTL
  • Issue lists: 30-second TTL
  • Historical reports: 1-hour TTL

Cache invalidation is time-based rather than event-based (since events arrive constantly, invalidating on every event would nullify caching).

Pillar 5
Alerting, Workflow Engine & ACI
5

Workflow Engine Architecture

In Sentry v26.x (2025–2026), the platform underwent a major migration to the Workflow Engine and ACI (Alert and Condition Interface) architecture. This separates concerns into discrete, composable components:

  • Detectors: Define what to watch — a data source (errors, metrics, uptime checks), evaluation conditions (thresholds, anomaly detection), and issue creation logic.
  • Data Sources: Abstracted streams of data feeding detectors (error events, trace metrics, custom application metrics).
  • Workflows: Define what to do when a detector fires. Contain a trigger (detector state change) and a sequence of actions.
  • Actions: Reusable notification and integration steps (Slack, PagerDuty, Jira).

Detector Evaluation

For metric alerts (e.g., "error rate > 5% over 5 minutes"), the detector queries pre-aggregated time-series buckets stored in ClickHouse or Redis. The evaluation happens in a dedicated alert evaluation consumer that reads from a Kafka topic of aggregated metrics. This decouples alert latency from raw event volume.

For issue alerts (e.g., "new issue created"), the evaluation is event-driven: the post-process consumer emits a notification event to Kafka, and the workflow engine evaluates whether any workflows subscribe to that issue type.

Open Periods & Metric Issues

A critical concept in the new system is the Open Period. When a detector fires, it creates an "open period" representing the active incident. The period tracks start time, duration, severity, associated events and traces, and resolution status. Open periods enable metric issues — issues created directly from metric detectors rather than individual events. This allows Sentry to represent "my checkout API has a high error rate" as a first-class issue with its own timeline, assignment, and resolution workflow.

AI-Powered Alerting

Recent versions have introduced AI-detected issues and Autofix. The platform uses Seer (Sentry's AI infrastructure) to:

  • Detect anomalous patterns in traces and logs that traditional threshold alerts miss.
  • Suggest root causes by analyzing stack traces, recent commits, and production changes.
  • Generate fix suggestions (Autofix) that can be reviewed and applied as pull requests.
⚙ Trade-off: Alerting

Latency vs. Accuracy: Alert evaluation must be fast (<1s) but accurate. Pre-aggregated metrics sacrifice per-event granularity for speed. Alert Fatigue: The system must prevent over-alerting through grouping (one issue, one alert), deduplication windows, and escalation policies. Running Autofix on every high-volume alert is expensive — the workflow gates this on impact (e.g., >1000 users/minute affected).

Pillar 6
Distributed Systems, Consistency & Multi-Region
6

Multi-Region Architecture

The architecture follows a multi-region active-active pattern with regional affinity:

  • Ingestion: Events are ingested at the nearest Relay edge (us-east, eu-west, asia-southeast). Relay validates and forwards to the regional Kafka cluster.
  • Processing: Regional consumers process events and write to regional ClickHouse and PostgreSQL replicas.
  • Querying: Users are routed to their "home" region (based on organization configuration) for querying, ensuring data locality.
  • Replication: Metadata changes (issue resolution, alert configuration) are replicated across regions using PostgreSQL logical replication or the outbox pattern.

The Outbox Pattern

For cross-region metadata consistency, Sentry uses the Transactional Outbox pattern. When an issue is resolved in us-east:

  1. The web application updates sentry_groupedmessage in the local PostgreSQL within a transaction.
  2. In the same transaction, it inserts a row into an outbox table.
  3. A background consumer reads the outbox, publishes the change to a cross-region Kafka topic.
  4. Regional consumers in eu-west and asia-southeast apply the change to their local PostgreSQL.

This provides eventual consistency for metadata across regions while preserving local ACID semantics. The outbox pattern is preferred over distributed transactions (2PC) because it decouples availability: if the cross-region link fails, local operations continue, and replication catches up later.

Pillar 7
Reliability Engineering & Operational Excellence
7

SLAs and Error Budgets

At Staff level, reliability is quantified. The system operates under an error budget: if the availability SLA is 99.99%, the system can be down for 4.32 minutes per month. This budget is consumed by planned maintenance, deployments, and unexpected outages. When the budget is exhausted, feature launches halt until reliability improves.

Backpressure & Circuit Breakers

The ingestion pipeline implements multiple layers of protection:

  • Relay backpressure: When Kafka is saturated, Relay stops reading HTTP requests, causing client SDKs to buffer locally or drop events (with telemetry).
  • Circuit breakers: If ClickHouse query latency exceeds a threshold, the query layer opens the circuit and returns cached or degraded results rather than cascading failure to the web tier.
  • Load shedding: During extreme overload (e.g., DDoS, misconfigured SDK sending infinite loops), the system drops events probabilistically based on project quotas and system health metrics.

Observability

The system must monitor itself with the same rigor it monitors customer applications:

  • RED Metrics: Rate (requests/sec), Errors (5xx rate), Duration (P50/P95/P99 latency) for every service.
  • Golden Signals: Ingestion lag (Kafka consumer lag), replication lag (PostgreSQL and ClickHouse), storage capacity, vacuum bloat.
  • Distributed Tracing: Every event is traced through Relay → Kafka → Consumers → PostgreSQL/ClickHouse/S3, with trace IDs propagated across service boundaries.

Pillar 8
Security, Privacy, Compliance & Multi-tenancy
8

Multi-Tenancy Isolation

Sentry is a multi-tenant SaaS. Strict isolation prevents:

  • Data leakage: Organization A must never see Organization B's events. Enforced at the API layer (every query includes organization_id and project_id filters) and at the database layer (row-level security policies).
  • Resource monopolization: Enforced via per-project rate limits, query timeouts (max_execution_time in ClickHouse), and resource quotas.

PII Scrubbing & Data Sanitization

Privacy is architected into the ingestion pipeline:

  • Server-side scrubbing: Relay applies regex-based rules to strip PII before events reach storage. Rules are configurable per project.
  • Hashing: User IDs and IP addresses may be one-way hashed for analytics while preserving anonymity.
  • Retention Policies: Automated jobs delete raw events after 90 days. ClickHouse partitions are dropped; S3 objects are lifecycle-managed.

GDPR Right to Erasure

When a user requests deletion, the system must:

  1. Remove the user from PostgreSQL (accounts, preferences).
  2. Purge all events containing the user's email/IP from ClickHouse (using mutations — expensive but necessary).
  3. Delete attachments and replays from object storage.
  4. Propagate deletion to downstream systems (Slack notifications, partner integrations).

This is implemented as an asynchronous deletion saga with idempotent steps and compensating actions for partial failures.

Encryption

  • At-rest: Database volumes (EBS/GCE PD) are encrypted. Object storage (S3/GCS) uses server-side encryption (AES-256). ClickHouse data is encrypted at the filesystem level.
  • In-transit: All service communication uses TLS 1.3. Internal service mesh provides mTLS between microservices.
  • In-use: Sensitive fields (integration tokens, DSN secrets) are encrypted in PostgreSQL using application-level encryption (e.g., AWS KMS or HashiCorp Vault) before storage.

End-to-End Real-World Simulation

Scenario: Black Friday E-Commerce Outage

📋 Context

You are the Staff Engineer responsible for the error tracking infrastructure at "ShopStream," a global e-commerce platform serving 50 million users. It is Black Friday. At 09:00 UTC, the checkout service deploys a bad release (v2.5.1) that nullifies the payment gateway response handler. Errors explode.

Phase 1 The Tsunami 09:00 – 09:05 UTC

Client Side

The checkout service runs Sentry SDK (Python) on 5,000 Kubernetes pods. Each pod throws AttributeError: 'NoneType' object has no attribute 'status_code' on every checkout attempt.

Ingestion

Event volume spikes from baseline 2,000 events/sec to 500,000 events/sec — a 250x burst.

Relay Edge

Regional Relays in us-east, eu-west, and asia-southeast see incoming HTTP connections spike. The token bucket rate limiters (backed by Redis) activate. ShopStream's project quota is 100,000 events/minute. Relay begins dropping excess events with 429 Too Many Requests and Retry-After: 60.

SDK Behavior

The Python SDK has a local buffer (100 events) and a background thread sender. When Relay returns 429, the SDK switches to client-side sampling, dropping 99% of events locally to prevent memory bloat in the application pods. This protects the checkout service from OOM kills during the incident — a critical design trade-off (sacrificing observability completeness for application stability).

Kafka Hot Partition

Despite the rate limiting, 100,000 events/sec still enter Kafka. The ingest-events topic has 100 partitions. Because partitioning is by project_id % 100, all ShopStream events land on a single partition. This creates a hot partition — one broker handles disproportionate load.

⚙ Staff Decision: Hot Partition

Kafka preserves per-project ordering, but the hot partition limits throughput to that partition's single consumer. If we partitioned by event_id instead, we'd distribute load but lose ordering (events for the same issue might be processed out of order, causing incorrect counter increments). The Staff decision: accept the hot partition and scale the consumer group vertically, or implement sub-partitioning (e.g., hash(project_id + event_id) % 1000 for ingestion, then re-order in a buffer stage).

Phase 2 Grouping & Issue Creation 09:01 UTC

Fingerprint Collision

All 100,000 events/minute share the same fingerprint: checkout/payment.py:process_response at line 42 + AttributeError. They map to a single issue, GROUP-12345.

PostgreSQL Write Load

The post-process consumer must update sentry_groupedmessage for GROUP-12345. With 100K events/minute, that's ~1,600 updates/second to the same row. PostgreSQL serializes these via row-level locks. The times_seen counter becomes a massive bottleneck.

Mitigation Strategy

The consumer does not update PostgreSQL on every event. Instead, it:

  1. Buffers increments in Redis (per-issue counters with 10-second TTL).
  2. Flushes to PostgreSQL every 5 seconds via UPDATE ... SET times_seen = times_seen + 50, last_seen = NOW().
  3. Uses advisory locks to serialize flushes per group ID, preventing multiple consumers from conflicting.
⚠ Trade-off

This introduces a 5-second lag in the issue counter. The UI shows "Seen 12,000 times" when the actual count might be 12,340. For an incident response, approximate counts are acceptable; precise counts can be reconciled later via ClickHouse aggregation.

Phase 3 Alerting & Workflow Engine 09:02 UTC

Detector Evaluation

The Workflow Engine has a detector configured: "If error rate on checkout transaction > 1% for 5 minutes, page the on-call engineer." The metrics consumer reads events and updates time-series counters in Redis/ClickHouse: errors_per_minute{transaction="checkout", release="v2.5.1"}.

Threshold Breach

At 09:02, the 5-minute rolling window shows 95% error rate. The detector fires, creating a metric issue (new in Sentry v26.x) titled "High error rate in checkout."

Workflow Execution

The workflow associated with this detector triggers:

  • PagerDuty: High-urgency page sent to the SRE rotation.
  • Slack: Message to #incidents channel with a link to the issue.
  • Autofix: The AI system (Seer) is triggered. It analyzes the stack trace, compares it to the GitHub commit history, and identifies that payment.py was modified in release v2.5.1 by commit abc123. It suggests a fix: add a null check for the gateway response.
⚙ Cost vs. Value Trade-off

Running Autofix on every high-volume alert is computationally expensive (LLM inference costs). The workflow gates this: Autofix only runs for issues affecting >1000 users/minute or critical transactions (checkout, payment). This is a cost-vs-value trade-off.

Phase 4 Query & Investigation 09:05 UTC

Engineer Response

The on-call engineer opens Sentry. The issue list query runs:

SQL 
SELECT id, title, count, last_seen 
FROM sentry_groupedmessage 
WHERE project_id = 42 AND status = 0 
ORDER BY score DESC LIMIT 20;

This uses the partial index on unresolved issues and returns in 50ms.

Trace Analysis

The engineer clicks into the issue. Sentry displays a trace waterfall showing the distributed trace: frontend → API gateway → checkout service → payment gateway. The trace reveals that the payment gateway returned 204 No Content (unexpected), and the checkout service crashed trying to parse it.

ClickHouse Query

SQL — Snuba Release Breakdown 
SELECT release, count(), uniq(user) 
FROM events 
WHERE group_id = 12345 
  AND timestamp > now() - 300 
GROUP BY release;

This shows 100% of errors are from release v2.5.1. ClickHouse processes this via vectorized aggregation over the last 5 minutes of data (a few million rows), returning in 200ms.

Phase 5 Resolution & Recovery 09:10 UTC

Rollback

The SRE triggers a rollback to v2.5.0. Error volume drops to zero within 2 minutes (pod restart time).

Issue Resolution

The engineer marks GROUP-12345 as resolved in v2.5.1. PostgreSQL updates the row: status = 1, resolved_at = NOW(), resolution_release = 'v2.5.1'.

Regression Detection

If v2.5.2 is deployed later and the same fingerprint reappears, Sentry detects a regression (the issue was resolved but recurred). This is implemented by comparing the event's release to resolution_release at ingestion time.

Post-Incident Analysis

  • Data Retention: Raw events from the incident are retained for 90 days in S3/ClickHouse, then moved to cold storage (Glacier) for compliance.
  • Aggregate Metrics: The error rate time-series is retained for 1 year in ClickHouse (downsampled to hourly buckets after 30 days).
  • Cost Analysis: The incident consumed 45 million events against ShopStream's monthly quota. The account manager reviews whether to adjust the plan or implement more aggressive client-side sampling.
Phase 6 Cross-Region Consistency (The Global View) 09:00 – 09:15 UTC

EU Data Residency

ShopStream has users in Germany. Their events were ingested in eu-west and never left the region. The German engineer investigating the incident sees the same issue data, but it was processed entirely within EU boundaries.

Global Dashboard

ShopStream's US headquarters views a dashboard aggregating error rates across all regions. The dashboard queries each regional ClickHouse cluster via the Synapse cell router and merges results. Because replication is asynchronous, the US dashboard shows asia-southeast data lagging by 3 seconds — an acceptable eventual consistency for a global overview.

L7/L8 Trade-off Synthesis: The Staff Engineer's Decision Framework

Throughout this deep-dive, the recurring theme is conscious trade-off selection. At the L7/L8 level, you are not expected to know every knob in PostgreSQL or ClickHouse. You are expected to reason about:

Consistency vs. Latency

We chose asynchronous counter updates (eventual consistency) to protect PostgreSQL from write hotspots, accepting a 5-second counter lag. For financial billing data, we would choose strong consistency despite the latency cost.

Completeness vs. Cost

We chose client-side sampling and rate limiting during the Black Friday surge. We lost 80% of error events, but preserved application availability. In a safety-critical system, we would choose backpressure with unbounded queues and horizontal scaling, accepting the cost.

Flexibility vs. Performance

The Workflow Engine's composable detectors/workflows provide powerful user customization but add evaluation overhead. We mitigate this with pre-aggregated metrics and caching. A simpler rule engine would be faster but less expressive.

Storage Efficiency vs. Query Speed

We store raw events in object storage and metadata in PostgreSQL/ClickHouse. This adds a network hop for full event retrieval but makes analytical queries 100x faster and cheaper than scanning JSON blobs.

Availability vs. Durability

Kafka acknowledges writes after replication to 3 brokers, providing durability with a slight latency penalty (milliseconds). For the web UI, we serve from read replicas that may lag by seconds, maximizing availability at the cost of fresh data.

Operational Complexity vs. Correctness

We rejected 2PC for cross-region metadata replication in favor of the outbox pattern. This introduces temporary inconsistency and requires reconciliation logic, but eliminates the availability risk of a coordinator failure.
